# v0.8: authenticated hybrid plus session resumption

**COMPLETE / SOFTWARE VALIDATED / CORE HARDWARE VALIDATED.**

v0.8 extends frozen v0.7: SMP remains disabled; full authentication uses
ML-KEM-768 + ephemeral application P-256, explicit human SAS comparison and
FINISHED_C/P. Protocol version and cryptographic domains are v0.8. A ticket is
committed only after successful authenticated full FINISHED completion.

The retained 32-byte `K_RESUME` permits a four-frame mutually authenticated
resume without ML-KEM, ECDH or SAS. Every resume has a fresh session ID, two
fresh nonces, new directional keys and confirmation keys. Ticket lifetime is
24 hours without renewal and at most 100 successful resumes; the Peripheral
stores one ticket only in RAM. Central tickets survive process restart.

The application data plane retains the actual v0.7 crypto worker and AES-GCM
primitives: Secure Data writes, explicit random IVs, role/session/type/sequence
AAD, strictly increasing receive sequences and three six-byte `PING n`/`PONG n`
rounds, **43-byte frames**. Both full and resumed sessions use this path. The
initial unfinished CP4 reuse was removed from v0.8 because it would introduce a
second experimental variable. Frozen v0.7 was not redesigned.

## Hardware validation

Real Windows ↔ nRF54L15 DK validation completed for the core v0.8 path.

### Full authenticated bootstrap

Validated on hardware:

- ML-KEM-768 public key: **1184 B**;
- ML-KEM ciphertext: **1088 B** over the MTU-247 fragment path;
- application P-256 contribution retained from frozen v0.7;
- operator SAS comparison completed successfully (`966182` in the recorded run);
- FINISHED verification completed;
- authenticated application state reached;
- three protected `PING n` / `PONG n` exchanges completed using the unchanged
  **43 B** v0.7-format frame.

The successful full bootstrap issued the RAM application-resumption ticket only
after authenticated full completion.

### Application resume

A subsequent real GATT reconnect successfully resumed the application session:

```text
resume
-> no ML-KEM
-> no application P-256
-> no SAS
-> fresh session_id / nonce_C / nonce_P
-> fresh directional traffic keys
-> APP_SECURE
-> 3 authenticated 43 B PING/PONG rounds
```

Repeated positive resumes were also observed, with the successful-use counter
advancing only on mutually authenticated resume completion.

### Negative hardware checks

The hardware campaign validated the important resume failure paths:

| Check | Result |
|---|---|
| forged / bad `RESUME_INIT` MAC | **PASS** — rejected locally |
| replayed duplicate `RESUME_INIT` | **PASS** — replay rejected |
| tampered `RESUME_ACCEPT` | **PASS** — Central rejects; `FINISH_C` not sent |
| replayed old `FINISH_C` in a fresh transcript | **PASS** — rejected |
| ticket survives failed attempt | **PASS** |
| positive resume after each failure | **PASS** |
| failed attempt does not consume successful-use count | **PASS** |

The negative tests confirm that malformed/authentication/replay failures do not
silently promote the session to `APP_SECURE` and do not destroy the still-valid
ticket.
