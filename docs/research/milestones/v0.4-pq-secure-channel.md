# Milestone v0.4 — Post-Quantum Secure Channel over BLE

**Date:** 2026-09-04  
**Project:** PQ-BLE-HANDSHAKE  
**Status:** ✅ Validated on real hardware

---

## 1. Objective

Milestone `v0.4-pq-secure-channel` extends the validated ML-KEM-768 BLE key-establishment flow into a real application-layer encrypted and authenticated channel.

```text
PC Central / liboqs
        |
        | ML-KEM-768 encapsulation
        | -> ciphertext
        | -> shared_secret_PC
        |
        | ciphertext over BLE/GATT
        v
nRF54L15 DK / mlkem-native
        |
        | ML-KEM-768 decapsulation
        | -> shared_secret_DK
        |
        | HKDF-SHA256
        | -> AES-256 session key
        |
        | AES-256-GCM
        | -> authenticated encrypted notification
        v
PC Central
        |
        | HKDF-SHA256
        | -> same AES-256 session key
        |
        | AES-256-GCM authentication + decryption
        v
"PQ-BLE SECURE CHANNEL"
```

Successful AES-GCM authentication is the primary end-to-end success criterion for the Phase 3 secure-channel path.

## 3. Cryptographic Construction

### 3.1 ML-KEM-768

The Central reads the dynamically generated ML-KEM public key from the nRF54L15 and encapsulates using liboqs. The DK decapsulates using mlkem-native.

| Item | Size |
|---|---:|
| Public key | 1184 B |
| Secret key | 2400 B |
| Ciphertext | 1088 B |
| Shared secret | 32 B |

### 3.2 HKDF-SHA256

Both endpoints derive the AES session key from the ML-KEM shared secret using:

```text
HKDF-SHA256
IKM  = ML-KEM shared secret
salt = "PQ-BLE-HANDSHAKE-v1"
info = "BLE-PQ-SESSION-KEY"
L    = 32 bytes
```

Output:

```text
AES-256 session key = 32 bytes
```

The ML-KEM shared secret and derived AES key are never transmitted or logged.

### 3.3 AES-256-GCM

The nRF54L15 encrypts the Phase 3 application message:

```text
PQ-BLE SECURE CHANNEL
```

using AES-256-GCM through PSA Crypto / nRF Security.

| Parameter | Value |
|---|---|
| AES key size | 256 bits |
| GCM IV | 12 B |
| GCM tag | 16 B |
| First sequence number | 0 |
| Data message type | `0x01` |
| Peripheral role | `0x02` |

The IV is generated at runtime through the PSA random API.

## 4. Session Context and AAD

The Central generates a fresh 16-byte `session_id` for each Phase 3 execution and sends:

```text
"START3" || session_id
```

Control payload:

```text
6 B  "START3"
16 B session_id
----------------
22 B total
```

AES-GCM AAD:

```text
session_id || sender_role || sequence_number || message_type
```

| Field | Size |
|---|---:|
| session_id | 16 B |
| sender role | 1 B |
| sequence number | 8 B |
| message type | 1 B |
| **Total AAD** | **26 B** |

The sequence number is encoded unsigned big-endian.

## 5. Secure Notification Wire Format

The existing Secure Data GATT characteristic is reused.

```text
sequence_number || message_type || IV || ciphertext || GCM_tag
```

For the 21-byte plaintext:

| Field | Size |
|---|---:|
| Sequence number | 8 B |
| Message type | 1 B |
| IV | 12 B |
| Ciphertext | 21 B |
| GCM tag | 16 B |
| **Total** | **58 B** |

## 9. Negative Security Tests

### 9.1 AES-GCM tag tampering

One bit of the received GCM tag was flipped on the Central before decryption.

```text
NEGATIVE TEST PASS: tampered AES-GCM message rejected
```

The unmodified original frame was subsequently authenticated and decrypted successfully.

**Validated property:** authenticated-encryption integrity / tag verification.

### 9.2 Wrong AAD / session binding

The Central attempted to decrypt the valid frame using a `session_id` differing by one bit.

```text
NEGATIVE TEST PASS: wrong session AAD rejected
```

The original session context still authenticated successfully.

**Validated property:** the frame is cryptographically bound to the session context through AES-GCM AAD.

### 9.3 Replay

After accepting the valid secure frame with sequence number `0`, the Central attempted to process the identical frame again.

```text
NEGATIVE TEST PASS: replayed secure frame rejected
```

**Validated property:** receiver-side replay/out-of-order protection in the current Central secure-channel implementation.

## 14. Current Limitations

This milestone is a validated research prototype, not yet the final protocol.

1. **Deterministic TEST-ONLY ML-KEM KeyGen coins**
   - the nRF54L15 ML-KEM keypair is still generated from fixed test coins;
   - production-quality ML-KEM randomness is not yet enabled.

2. **One-direction initial secure application flow**
   - validated secure application traffic is currently Peripheral → Central;
   - full bidirectional encrypted application traffic is pending.

3. **Handshake authentication not yet fully integrated**
   - the isolated Phase 3 path bypasses the legacy SAS flow;
   - transcript-bound SAS / FINISHED-style confirmation is not yet part of the final embedded protocol.

4. **No hybrid classical + PQ key establishment yet**
   - no application-layer P-256 ECDH;
   - no ECDH + ML-KEM combiner.

5. **No official performance benchmark yet**
   - debug timestamps include scheduling and logging effects;
   - per-operation benchmark instrumentation is still required.

6. **No energy measurements yet**

7. **No formal verification yet**

8. **liboqs environment mismatch**
   - runtime 0.15.0 vs liboqs-python 0.16.0 should be aligned before formal experiments.

## 15. Milestone Conclusion

`v0.4-pq-secure-channel` demonstrates a complete post-quantum application-layer secure channel over real Bluetooth Low Energy between:

```text
PC Central / liboqs
        ↕ BLE/GATT
Nordic nRF54L15 DK / mlkem-native + PSA Crypto
```

The validated end-to-end path is:

```text
ML-KEM-768
    ↓
HKDF-SHA256
    ↓
AES-256-GCM
    ↓
authenticated encrypted BLE application data
```

The Central successfully recovers:

```text
PQ-BLE SECURE CHANNEL
```

with a valid AES-GCM authentication tag. Tampering, wrong session AAD, and replay attempts were rejected in the corresponding negative tests.

This milestone upgrades the project from a post-quantum key-establishment demonstrator to a working post-quantum encrypted and authenticated BLE application channel.

## 16. Next Milestone

Recommended next milestone:

```text
v0.5 — Production randomness and authenticated PQ handshake
```

Primary goals:

1. replace deterministic ML-KEM KeyGen coins with production-quality randomness on the nRF54L15;
2. retain the validated ML-KEM → HKDF → AES-GCM data path;
3. bind the complete handshake transcript;
4. integrate SAS / explicit FINISHED-style confirmation;
5. define the authenticated session establishment that will later be reused by the hybrid P-256 + ML-KEM protocol.

Bidirectional secure application traffic can then be added before moving to the hybrid key-establishment phase.
