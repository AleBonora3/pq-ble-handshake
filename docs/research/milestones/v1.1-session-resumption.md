# v1.1: bonded SMP L4 plus ML-KEM application resumption

**COMPLETE / SOFTWARE VALIDATED / CORE HARDWARE VALIDATED.**

v1.1 extends frozen v1.0. BLE authenticated LE Secure Connections L4 remains
mandatory, with a 16-byte link key and the existing Numeric Comparison/bonding
ceremony. Full application authentication uses ML-KEM alone for its PRK and
the CP3 transcript/FINISHED chain. No SMP DHKey or LTK is mixed into
`K_RESUME`. The application data plane retains CP4 framing, AAD, derived nonce
construction, exact-next sequences and two 16-byte challenge/echo rounds,
**51 bytes per frame**. Its explicit wire version and domain are v1.1.

After authenticated full FINISHED completion, a separate RAM-only application
ticket can resume within 24 hours and 100 successful uses. A successful bonded
resume first restores BLE L4 and then runs the four symmetric resume frames with
fresh session ID, nonces and traffic keys. It skips ML-KEM and does not run a
new Numeric Comparison ceremony.

The BLE bond and application ticket are intentionally separate:

```text
BLE bond
   !=
application resume ticket
```

A DK reboot retains BLE settings but loses the RAM application ticket. The next
bonded connection therefore restores authenticated L4, receives a controlled
resume rejection, executes a full ML-KEM fallback, issues a new ticket and
returns to `APP_SECURE`.

The application ticket binds to `bt_conn_get_dst()` (resolved LE identity in the
installed NCS v3.0.0) as address type plus six bytes. Identity shape and an
actual matching default-local-identity bond are required. Resume additionally
requires the bond to have existed at connect. Registered bond deletion/new
pairing invalidates the application-resumption context; loss of L4 aborts
application state.

## Software validation and first-CP4 audit

A real-hardware failure exposed two integration bugs during final v1.1
validation:

1. the CP3 strict SEC_INFO comparison was initially hard-coded to v1.0 profile
   `0x10` instead of using the active profile;
2. after that correction, successful v1.1 CP3 left the consumed ciphertext slot
   in `CIPHERTEXT_CRYPTO_BUSY`, causing the outer v1.1 Control dispatcher to
   reject the first CP4 frame with ATT `0x13`.

The final scoped fix clears the consumed ciphertext reservation **only for
v1.1**, after successful key/service commit and before publishing
`V1_CP3_APP_SECURE`, while `protocol_lock` is held. The notification-ordering fix
also keeps the successful `FINISHED_P` queue/commit transition serialized against
an immediate CP4 receive.

The production-code regression harness now exercises the actual v1.1 Control
dispatcher, CP3 worker commit, resume service and immediate/delayed/concurrent
first CP4.

## Core hardware validation

Final validation was executed on the real Windows Central ↔ nRF54L15 DK path at
ATT MTU 247.

### Cold full handshake

Validated:

- all four protected PQ GATT operations denied before authenticated L4;
- cold SMP LE Secure Connections Numeric Comparison;
- resulting `level=L4`, `SC=YES`, `authenticated=YES`, encryption key size 16,
  PQ gate open and profile `0x11`;
- ML-KEM-768 public-key read (**1184 B**);
- ML-KEM ciphertext write (**1088 B**, five fragments);
- `START_CP3` accepted;
- transcript/HKDF processing PASS;
- `FINISHED_C` verification PASS;
- Peripheral RAM ticket issued;
- `APP_SECURE`;
- **two authenticated CP4 round trips** using the 51 B application frame.

Central success marker:

```text
Profile 0x11 full: APP_SECURE, 2 authenticated round trips; ticket=True
```

The first CP4 write may be logged by the DK before the later APP_SECURE log
because the entry log occurs before mutex acquisition. Successful ATT completion
and authenticated PONG verification are the acceptance criteria.

### Repeated bonded resume

Two consecutive bonded reconnections restored L4 without another Numeric
Comparison and completed application resumption without ML-KEM.

Peripheral markers included:

```text
RES mutual confirmation: fresh keys/IVs; APP_SECURE; no ML-KEM/P-256/SAS; count=1
RES mutual confirmation: fresh keys/IVs; APP_SECURE; no ML-KEM/P-256/SAS; count=2
```

Both sessions completed two authenticated CP4 round trips.

### DK reboot / full fallback

After DK reset:

- the BLE bond persisted;
- the Peripheral RAM ticket was gone;
- the Central attempted resume;
- the Peripheral returned a generic `RESUME_REJECT`;
- authenticated L4 remained established;
- the Central automatically executed the full ML-KEM path;
- a new RAM ticket was issued;
- two authenticated CP4 round trips passed;
- the next bonded connection resumed successfully with the new ticket.

This validates that a BLE bond alone is insufficient for application resumption.

### Negative hardware validation

| Check | Result |

| bad `RESUME_INIT` MAC | **PASS** |
| replayed duplicate `RESUME_INIT` | **PASS** |
| tampered `RESUME_ACCEPT` | **PASS** — Central rejects; `FINISH_C` not sent |
| replayed old `FINISH_C` in fresh transcript | **PASS** |
| ticket retained after each failed attempt | **PASS** |
| positive resume after each failure | **PASS** |
| failed attempts do not consume successful-resume count | **PASS** |

The Peripheral successful-resume counter advanced only on real mutually
authenticated completions. Recovery resumes after the negative checks reached
the expected successive counts.

### Bond deletion / new pairing lifecycle

With the old application context deliberately not used as a substitute for link
authentication:

- Windows bond removed;
- DK bond removed;
- DK reset;
- next connection classified as cold;
- all four protected PQ GATT probes denied before L4;
- a new Numeric Comparison was mandatory;
- full ML-KEM/CP3 ran;
- a new ticket was issued;
- two CP4 round trips passed;
- the following connection resumed normally with `count=1`.

Central reported:

```text
Full-handshake fallback: NO_TICKET
```

This confirms the security property that application resumption cannot bypass a
new authenticated SMP L4 pairing after bond deletion.
