## Motivation and difference from v0.7

v0.7 is an *application-level authenticated hybrid handshake*: ML-KEM-768 and
an application-layer P-256 ECDH both feed the same HKDF key schedule
(`SS_MLKEM || SS_ECDH`), peers are authenticated by an application-layer SAS
Numeric Comparison, and the firmware runs with `CONFIG_BT_SMP=n`.

v1.0 is a **layered classical/PQ architecture**: classical peer
authentication and BLE link protection are delegated to the standard
Bluetooth Security Manager (authenticated LE Secure Connections, Numeric
Comparison, Security Mode 1 Level 4). The application layer keeps only
ML-KEM-768, a transcript-bound HKDF key schedule, FINISHED and AES-256-GCM.
The application-level P-256 ECDH, the hybrid combiner, `K_sas` and the
application SAS are removed from the v1.0 path (CP3). v1.0 is therefore
*not* a hybrid key establishment and must not be described as one.

```text
BLE connection
      |
BLE SMP Security Mode 1 Level 4         classical (P-256, SMP)
  authenticated LE Secure Connections
  Numeric Comparison, MITM protection
  BLE Link Layer encryption
      |
ML-KEM-768 over protected GATT          post-quantum (CP2)
      |
transcript-bound HKDF-SHA256            (CP3)
FINISHED_C / FINISHED_P
      |
AES-256-GCM application channel         keys derived from SS_MLKEM (CP4)
```

Security separation (claims and non-claims):

| Layer | Mechanism | Post-quantum? |
|---|---|---|
| Peer authentication | BLE SMP Level 4 (P-256, Numeric Comparison) | **no** |
| BLE link encryption | BLE Link Layer, LTK from SMP | **no** |
| Application key establishment | ML-KEM-768 | yes |
| Application payload protection | AES-256-GCM with ML-KEM-derived keys | yes (symmetric) |

The SMP secret (LTK/DHKey) is **not** combined with `SS_MLKEM`. The string
`BLE-SMP-SM1-L4` planned for the v1.0 transcript is an application-level
context label, not a cryptographic exporter from the SMP secret. The guarantee
that the ML-KEM exchange happens inside a Level 4 link comes from the BLE
security state, GATT gating and state-machine enforcement.

## CP1 — SMP Level 4 foundation

### What CP1 proves

```text
NO L4  -> NO PQ GATT ACCESS  -> NO PQ HANDSHAKE
AUTHENTICATED L4 -> PQ GATT ACCESS ALLOWED
```

CP1 does **not** change the ML-KEM key schedule. The v0.7 key schedule is
untouched; the v1.0 key schedule is defined in CP3.

### Firmware profile

The v0.7 baseline (`prj.conf`, `CONFIG_BT_SMP=n`) is frozen. v1.0 is selected
by the extra Kconfig fragment `firmware/v1_smp_l4_mlkem.conf`, which sets the
Kconfig choice `PQ_PROFILE` to `PQ_PROFILE_V10_SMP_L4_MLKEM`. Both profiles
share `main.c`, the ML-KEM worker, ciphertext fragmentation, PSA Crypto and
the GATT layout (same UUIDs and attribute indices). Only the v1.0 profile
compiles `pq_v1_security.c` and `pq_v1_frame.c`.

Kconfig symbols were verified against `sdk-zephyr` tag `v4.0.99-ncs1`
(NCS 3.0.0):

| Symbol | Effect verified in source |
|---|---|
| `CONFIG_BT_SMP=y` | Security Manager; selects `BT_ECC` (SMP ECDH via PSA) |
| `CONFIG_BT_SMP_SC_ONLY=y` | selects `BT_SMP_SC_PAIR_ONLY`; `bt_conn_set_security()` and `remote_sec_level_reachable()` force **L4**; Just Works is rejected with *authentication requirements* |
| `CONFIG_BT_SMP_ENFORCE_MITM=y` | MITM flag whenever the IO capability allows it (default y) |
| `CONFIG_BT_SMP_MIN_ENC_KEY_SIZE=16` | default under SC-only; L4 requires a 16-octet key |
| `CONFIG_BT_BONDABLE=y`, `CONFIG_BT_SMP_ALLOW_UNAUTH_OVERWRITE=n`, `CONFIG_BT_MAX_PAIRED=2` | bonding; an unauthenticated peer cannot overwrite a bond |
| `CONFIG_BT_SETTINGS=y`, `CONFIG_SETTINGS=y`, `CONFIG_ZMS=y`, `CONFIG_FLASH=y`, `CONFIG_FLASH_MAP=y` | bond persistence on the nRF54L15 RRAM (`storage` partition, 36 KiB, 4 KiB erase blocks → 9 ZMS sectors). `settings_load()` runs after `bt_enable()` |
| `CONFIG_DK_LIBRARY=y` | DK buttons (sdk-nrf v3.0.0 `dk_buttons_and_leds`) |

Application options (`firmware/Kconfig`): `PQ_V1_NUMERIC_COMPARISON_TIMEOUT_MS`
(default 60 000), `PQ_V1_BUTTON_UI` (default y), `PQ_V1_CLEAR_BONDS_ON_BOOT`
(TEST ONLY, default n).

### SMP callbacks and IO capability

`pq_v1_security.c` registers `passkey_display` **and** `passkey_confirm`
(plus the mandatory `cancel`), which is exactly what makes the Zephyr host
advertise the *DisplayYesNo* IO capability (`smp.c`, `get_io_capa()`). With a
DisplayYesNo Central this yields **Numeric Comparison**; with a KeyboardOnly
Central it selects Passkey Entry, which this CP1 profile now refuses because
it requires Numeric Comparison with a decision on both peers; with a
NoInputNoOutput Central it would yield Just Works, which SC-only mode
rejects.

The `passkey_confirm` callback only logs the value, references the connection
and starts the timeout. **It never calls `bt_conn_auth_passkey_confirm()`**;
that call happens only from the DK button handler (system workqueue):

| Button (DK library) | devicetree | silkscreen (nRF54L15 DK) | action |
|---|---|---|---|
| `DK_BTN1` | `sw0` | BUTTON 0 | ACCEPT the Numeric Comparison |
| `DK_BTN2` | `sw1` | BUTTON 1 | REJECT (`bt_conn_auth_cancel`) |
| `DK_BTN4` | `sw3` | BUTTON 3 | delete all bonds (only while no connection exists) |

Handled events: confirm, reject, stack/peer cancel, timeout
(`bt_conn_auth_cancel` + disconnect with `BT_HCI_ERR_AUTH_FAIL`), pairing
failed, pairing complete (bonded flag), bond deleted, security changed with
error, security downgrade, disconnect during the comparison (reference
released, timeout cancelled, state invalidated).

Expected DK log for a cold pairing:

```text
BLE connected: <addr>
Cold link: waiting for Central custom pairing; PQ GATT gate CLOSED
Incoming SMP: peer IO=<reported IO> auth=<reported flags> max_key=16
Numeric Comparison requested: <addr>
NUMERIC COMPARISON VALUE: 123456
BUTTON 0 = ACCEPT    BUTTON 1 = REJECT
Numeric Comparison ACCEPTED by operator (123456): 0
SMP pairing complete: <addr>
Bond created = YES
Security changed: <addr>
Security level = L4
Secure Connections = YES
Authenticated link = YES
Encryption key size = 16 octets
PQ GATT gate: OPEN (authenticated Security Mode 1 Level 4)
```

### v1.0 security state machine (CP1 part)

```text
DISCONNECTED -> CONNECTED_UNSECURED -> SMP_PAIRING -> NUMERIC_COMPARISON -> L4_SECURED
                                     \-> FAILED (pairing failure, rejection, timeout, downgrade)
```

Cold peers wait for Central-initiated SMP. Only a stored DK bond triggers
`bt_conn_set_security(L4)` for encryption restoration.
`CONFIG_BT_GATT_AUTO_SEC_REQ=n` disables a second implicit initiator.
SC-only enforces L4 for incoming SMP too (`remote_sec_level_reachable`).
One pairing attempt is allowed per connection; failed attempts reconnect.

Any disconnect returns to `DISCONNECTED` and invalidates the context. The
CP3 states (`PQ_CRYPTO_BUSY`, `WAIT_FINISHED_C`, `FINISHED_BUSY`,
`APP_SECURE`, `DATA_BUSY`) can only be entered from `L4_SECURED`.

### GATT security gating

Permissions in the v1.0 profile:

| Attribute | v0.7 | v1.0 |
|---|---|---|
| Public Key value | `READ` | `READ_AUTHEN \| READ_LESC` |
| Ciphertext value | `WRITE` | `WRITE_AUTHEN \| WRITE_LESC` |
| Secure Data value | `WRITE` (+ notify) | `WRITE_AUTHEN \| WRITE_LESC` |
| Secure Data CCCD | `READ \| WRITE` | `READ_AUTHEN \| READ_LESC \| WRITE_AUTHEN \| WRITE_LESC` |
| Control value | `WRITE` | `WRITE_AUTHEN \| WRITE_LESC` |

In Zephyr 4.0.99 `bt_gatt_check_perm()` returns *Insufficient Authentication*
(0x05) when no LTK exists or the link is not authenticated (`< L3`) or not
LESC, and *Insufficient Encryption* (0x0F) when an LTK exists but the link is
not encrypted. `AUTHEN` alone accepts L3 and `LESC` alone accepts an
unauthenticated Secure Connections link, so **permission bits do not express
Level 4**. Every sensitive callback (`read_public_key`, `write_ciphertext`,
`write_secure_data`, `write_control`) therefore first calls
`pq_gatt_security_gate()`, which requires `pq_v1_security_conn_is_l4()`:

1. the connection is the tracked one and its `security_changed` callback
   reported L4 without error in the current connection generation (state machine), **and**
2. the host currently reports `bt_conn_get_security() == BT_SECURITY_L4`,
   `BT_SECURITY_FLAG_SC` and a 16-octet key (`bt_conn_get_info`,
   `bt_conn_enc_key_size`).

Failure returns ATT 0x05. CCCD reads use the same runtime gate; writes use
the pinned stack's managed `cfg_write` validation hook. Its original write
function is retained so Zephyr still recognizes the CCCD for bond storage
and restoration. SEC_INFO notifications recheck the runtime gate at send time.
No legacy handshake is submitted in this profile.

In the v1.0 profile the Control characteristic rejects every v0.x frame
(`START`, `START3`, `START5`, `PQS5`, `PQS7`, `PQBL`) even at Level 4, so the
v0.7 hybrid handshake can never be run "on top of SMP" by mistake.

### PQV1 framing (CP1 subset)

```text
magic "PQV1" (4) || version 0x10 (1) || subtype (1) || payload_len u16be (2) || payload
```

| Subtype | Direction | Payload | Meaning |
|---|---|---|---|
| `0x01 SEC_QUERY` | C→P (Control) | 0 B | ask the DK to attest its link security |
| `0x02 SEC_INFO` | P→C (Secure Data notify) | `level(1) flags(1) enc_key_size(1) profile(1)` | `flags`: bit0 SC, bit1 authenticated, bit2 gate open; `profile` = 0x10 |
| `0x7F ERROR` | P→C | `status(1)` | 0x10 insufficient security, 0x11 legacy control rejected, 0x12 invalid state, 0x13 notifications disabled, 0x14 unsupported subtype |
| `0x10`–`0x13` | reserved | — | `START_V1`, `READY_V1`, `FINISHED_C`, `FINISHED_P` (CP2/CP3) |

`SEC_INFO` is DK-side evidence that lands in the PC log. The Central accepts
it only when `level == 4`, SC, authenticated, gate open, key size 16 and
profile 0x10 (`is_authenticated_level4()`); anything weaker fails closed.

### Windows Central

The installed Bleak 3.0.2 pairer supports `CONFIRM_ONLY` and automatically
accepts that ceremony; it also has protection-level fallback logic. CP1 uses
its own `DeviceInformationCustomPairing` positive path: exactly
`CONFIRM_PIN_MATCH` (8), minimum `ENCRYPTION_AND_AUTHENTICATION` (3), with no
fallback. Windows PairingKinds is a ceremony mask, not an API for directly
forcing on-air SMP IO capabilities. The final DK L4 attestation is mandatory.

The exact `DeviceInformation.id` comes from Bleak's live WinRT requester.
That ID is retained across OS disconnect and used for fresh pairing-state
queries. The synchronous handler is registered before PairAsync. It obtains
a deferral on the event thread, schedules the human decision on asyncio, and
calls Accept only for explicit boolean consent. PairAsync completion,
exception, timeout or cancellation invalidates the ceremony, completes the
deferral once, cancels/drains pending decisions and unregisters the handler.
Native timeout/cancellation also cancels the WinRT operation. Handler errors
propagate instead of being mistaken for security rejection.

The PC input is the **Python console prompt** carrying Windows' PIN; a
separate Windows consent UI may also appear. Do not rely on a separate OS
Numeric Comparison dialog. Console input is cancellable and does not leave
an executor thread blocked in `input()` after pairing aborts. Complete both
human decisions promptly: the application timeout is 60 seconds but the
pinned SMP transaction timer is 30 seconds and can expire sooner.

Successful cold pairing requires this handler's explicit NC acceptance,
PAIRED status and a refreshed authenticated Windows bond. An already-paired
race fails the cold test; the normal bonded scenario skips pairing/probes
and still requires strict DK SEC_INFO. Stale bonds require clearing both
stores. Reconnection uses a fresh advertisement from the original address,
then a new Bleak client, so a same-name peripheral cannot replace the peer.

### CP1 Central flow

```text
scan/connect (Bleak, MTU logged)
cold pairing only:
  probe Public Key read      -> must be a security denial
  probe Ciphertext write     -> must be a security denial
  probe Control write        -> must be a security denial
  probe Secure Data CCCD     -> must be a security denial
  WinRT CONFIRM_PIN_MATCH pairing, human confirmation on PC and DK
  outcome must be PAIRED with ENCRYPTION_AND_AUTHENTICATION
bonded reconnect: probes and pairing skipped
post-L4:
  subscribe CCCD, read Public Key (1184 B), write a real ML-KEM ciphertext
  (SS discarded; no START), write SEC_QUERY, receive SEC_INFO
  accept only strict authenticated L4 -> state L4_GATT_VERIFIED
```

Any success before L4 is reported as `GATING FAILURE`; any non-security
failure (busy, invalid length, unreachable, disconnect) fails CP1 rather than
counting as a denial.

Negative modes (`--v1-negative`):

| Mode | Required evidence |
|---|---|
| `pre-l4-only` | Four security denials. Log says Central custom pairing was not invoked; inspect DK for unsolicited SMP. |
| `nc-reject` | Real CONFIRM_PIN_MATCH callback and explicit PC `no`, failed pairing, no Windows bond, then four denials on a fresh unpaired connection. |
| `just-works` (legacy name) | Windows CONFIRM_ONLY application ceremony with minimum ENCRYPTION (2); a specific security refusal, or generic FAILED only after observing/accepting that ceremony; no bond and four fresh denials. Does not establish the on-air BLE association method. |

After a supported rejection, the old GATT session is always retired before
probing again; an expected disconnect is not an infrastructure failure.
The Central waits for the original peer to advertise again before reconnecting.
Neither bond store is deleted during verification, so an accidental bond is
not erased as evidence. A successful PQ operation, a bond, or a notification
fails the negative test. Failure to obtain the fresh verification connection
is **inconclusive**, with a nonzero exit status, never PASS.

A generic FAILED before a callback, a timeout, missing handler, access-denied
setup failure, or busy operation is insufficient rejection evidence. A
**DK-only rejection** after PC `yes` also needs the UART history: Windows'
final authentication failure cannot exclude a failure after encryption/key
distribution. The automated NC test therefore uses PC `no`. The DK BUTTON 1
case remains a separate UART-correlated hardware check, not an automatic PASS.

The four probes prove access denial at the sampled points, not a historical
trace of the firmware gate. The full hardware oracle combines those results
and ceremony evidence with the DK log: **no L4, no gate OPEN throughout the
negative attempt and its verification connection**. WinRT cannot prove an
on-air Just Works association by a ceremony mask alone; a supported negative
PASS proves refusal of the CONFIRM_ONLY-only path. Microsoft defines
`DevicePairingKinds` in terms of application-supported/system-requested
pairing ceremonies, with `ConfirmOnly` requesting application consent.
[DevicePairingKinds](https://learn.microsoft.com/en-us/uwp/api/windows.devices.enumeration.devicepairingkinds?view=winrt-26100)
Do not claim a radio-level Just Works test without corresponding DK/trace evidence.

The CLI distinguishes `NEGATIVE TEST: INCONCLUSIVE` (exit 1) from a failed
security check. In `just-works` mode it also reports `CONFIRM_ONLY FAIL-CLOSED:
INCONCLUSIVE (insufficient automated evidence)` and `RADIO-LEVEL JUST WORKS:
NOT DEMONSTRATED`. A supported rejection followed by all required checks
instead reports `CONFIRM_ONLY FAIL-CLOSED: PASS` (exit 0), still with
`RADIO-LEVEL JUST WORKS: NOT DEMONSTRATED`. A bond, successful PQ access or
notification remains FAIL. Generic FAILED without a callback remains
inconclusive; no security-evidence predicate or pairing behavior is relaxed.
