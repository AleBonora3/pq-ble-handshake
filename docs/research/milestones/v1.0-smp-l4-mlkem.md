## Motivation and difference from v0.7

v0.7 is an **application-level authenticated hybrid handshake**:

```text
ML-KEM-768
    +
application P-256 ECDH
    |
    v
SS_MLKEM || SS_ECDH
    |
    v
HKDF
    |
    +--> application SAS
    +--> FINISHED
    +--> AES-256-GCM
```

The v0.7 firmware runs with:

```text
CONFIG_BT_SMP=n
```

so its security properties are intentionally built above GATT.

v1.0 is a different architecture.

It is a **layered classical/PQ design**:

```text
BLE connection
      |
      v
BLE SMP Security Mode 1 Level 4
authenticated LE Secure Connections
Numeric Comparison
MITM protection
BLE Link Layer encryption
      |
      v
protected PQ GATT operations
      |
      v
ML-KEM-768
      |
      v
transcript-bound v1 key schedule        CP3
FINISHED_C / FINISHED_P
      |
      v
AES-256-GCM application channel         CP4
```

The application-level P-256 ECDH used by v0.7 is removed from the v1 path.

The v1 design therefore has:

- no application-level P-256 ECDH;
- no `SS_MLKEM || SS_ECDH` hybrid combiner;
- no application SAS;
- no `K_sas`;
- no export of the BLE SMP LTK or SMP DHKey into the application KDF.

The SMP secret and `SS_MLKEM` remain cryptographically separated.

### Security separation

| Layer | Mechanism | Post-quantum? |
|---|---|---|
| Peer authentication | BLE SMP Level 4, P-256, Numeric Comparison | no |
| BLE link encryption | BLE Link Layer using SMP-derived LTK | no |
| Application key establishment | ML-KEM-768 | yes |
| Application traffic protection | AES-256-GCM with ML-KEM-derived keys | symmetric/PQ-resistant against quantum key search at appropriate key size |

The v1 security claim must therefore remain precise:

> BLE SMP Level 4 provides classical authenticated peer association and
> link-layer protection. ML-KEM provides the post-quantum application
> key-establishment secret.

v1.0 must **not** be described as a hybrid key agreement.

## CP1 security state machine

The CP1 state progression is:

```text
DISCONNECTED
    |
    v
CONNECTED_UNSECURED
    |
    v
SMP_PAIRING
    |
    v
NUMERIC_COMPARISON
    |
    v
L4_SECURED
```

Failure paths include:

```text
pairing rejection
pairing failure
timeout
security error
security downgrade
disconnect
```

Any disconnect invalidates the active security context.

CP2 adds the temporary `PQ_CRYPTO_BUSY` operation after `L4_SECURED`.

CP3 will later add the FINISHED/application-security states.

---

## Strict Level-4 predicate

GATT permission bits alone are not treated as sufficient evidence of L4.

Every PQ-sensitive operation is additionally protected by the runtime
security gate.

The authoritative predicate requires:

```text
current tracked connection
+
security state == L4_SECURED
+
bt_conn_get_security() == BT_SECURITY_L4
+
Secure Connections flag present
+
authenticated link
+
16-byte encryption key
```

If any condition fails, PQ access fails closed.

---

## PQ GATT gating

Sensitive operations include:

- Public Key read;
- Ciphertext write;
- Secure Data access;
- Secure Data CCCD;
- Control write.

Before L4 they must fail.

After strict L4 they may become accessible.

The v1 Control characteristic rejects the legacy v0.x protocol frames so the
v0.7 hybrid handshake cannot accidentally execute inside the v1 profile.

---

## PQV1 framing — CP1 + CP2

The v1 control protocol is versioned independently from the older v0.x
application frames.

Wire format:

```text
magic "PQV1" (4)
|| version 0x10 (1)
|| subtype (1)
|| payload_len u16be (2)
|| payload
```

### Implemented / reserved subtypes

| Subtype | Direction | Payload | Meaning |
|---|---|---|---|
| `0x01 SEC_QUERY` | C -> P | 0 B | request DK-side security attestation |
| `0x02 SEC_INFO` | P -> C | 4 B | current security state |
| `0x10 START_V1` | C -> P | `session_id(16)` | CP2 ML-KEM decapsulation request |
| `0x11 READY_V1` | P -> C | `diagnostic(32)` | CP2 TEST-ONLY shared-secret diagnostic |
| `0x12 FINISHED_C` | C -> P | reserved | CP3 |
| `0x13 FINISHED_P` | P -> C | reserved | CP3 |
| `0x7F ERROR` | P -> C | status | fail-closed protocol/security error |

### SEC_INFO

The Central accepts `SEC_INFO` only when all of the following are true:

```text
level == L4
Secure Connections == YES
authenticated == YES
encryption key size == 16
PQ GATT gate == OPEN
profile == 0x10
```

Anything weaker fails closed.

`FINISHED_C` and `FINISHED_P` remain unsupported during CP2.

# CP2 — ML-KEM-768 over authenticated SMP Level 4

## CP2 goal

CP2 adds one capability and proves one property:

> Run a real ML-KEM-768 encapsulation/decapsulation exchange over the already
> authenticated Level-4 link and prove that both peers independently obtain
> the same `SS_MLKEM`.

CP2 does **not** yet create the final v1 application secure channel.

---

## CP2 execution chain

```text
authenticated BLE SMP Security Mode 1 Level 4
        |
        | PQ GATT gate OPEN
        v
read DK ML-KEM-768 public key
        |
        v
Central ML-KEM-768 encapsulation
        |
        +--> CT = 1088 B
        +--> SS_MLKEM_C = 32 B
        |
        v
ciphertext transfer over protected GATT
        |
        v
START_V1
        |
        v
DK ML-KEM-768 decapsulation
        |
        +--> SS_MLKEM_P = 32 B
        |
        v
TEST-ONLY HMAC diagnostic
        |
        v
READY_V1
        |
        v
constant-time diagnostic comparison
        |
        v
MATCH -> CP2 PASS
```

The SMP LTK or SMP DHKey is never combined with `SS_MLKEM`.


## CP2 TEST-ONLY diagnostic

CP2 uses the following interoperability diagnostic:

```text
transcript_digest =
    SHA256(
        ML-KEM_public_key ||
        ML-KEM_ciphertext
    )
```

Then:

```text
diagnostic =
    HMAC-SHA256(
        key = SS_MLKEM,
        data =
            "PQ-BLE-HANDSHAKE-v1.0/CP2-DIAGNOSTIC"
            || session_id
            || transcript_digest
    )
```

Output size:

```text
32 B
```

The Central calculates its expected diagnostic from the shared secret returned
by ML-KEM encapsulation.

The nRF54L15 DK independently calculates the diagnostic from the shared secret
returned by mlkem-native decapsulation.

The Central compares the two values with a constant-time comparison.

### Important scope limitation

This construction is explicitly:

```text
TEST ONLY
```

It is **not**:

- the final v1 FINISHED;
- a production application authenticator;
- the CP3 transcript/key schedule;
- an application traffic key;
- an application SAS.

It exists only to prove CP2 ML-KEM interoperability without transmitting the
raw shared secret.

## Firmware CP2 implementation

`START_V1` is accepted only if:

- the caller is the current tracked connection;
- the live connection still satisfies strict L4;
- notifications are enabled;
- the CCCD is actually subscribed;
- the ML-KEM keypair is ready;
- the ciphertext has been fully reassembled;
- the ciphertext length is exactly 1088 B;
- no incompatible crypto operation is active;
- no stale crypto connection reference exists;
- the session identifier is exactly 16 B.

Heavy cryptographic work is not performed inside the GATT callback.

The CP2 operation uses the dedicated ML-KEM worker mode:

```text
PQ_MLKEM_JOB_V1_CP2
```

and the dedicated submission API:

```text
pq_mlkem_session_submit_v1_cp2(...)
```

The worker:

1. consumes the completed ML-KEM ciphertext;
2. performs real ML-KEM-768 decapsulation;
3. obtains a temporary local `SS_MLKEM`;
4. computes the TEST-ONLY CP2 diagnostic;
5. clears the shared secret and temporary cryptographic state;
6. returns only the encoded READY response.

---

## CP2 lifecycle

CP2 uses only a temporary crypto-busy state:

```text
L4_SECURED
    |
    | START_V1
    v
PQ_CRYPTO_BUSY
    |
    | ML-KEM decapsulation
    | + TEST-ONLY diagnostic
    v
L4_SECURED
```

Successful CP2 completion does **not** enter:

```text
WAIT_FINISHED_C
FINISHED_BUSY
APP_SECURE
DATA_BUSY
```

No application traffic keys exist at CP2.

Those are later-checkpoint concerns.

---

## Disconnect, downgrade and stale-job protection

CP2 is invalidated by:

- disconnect;
- security downgrade;
- security error;
- disabled notification subscription;
- connection-generation mismatch;
- stale originating connection;
- incompatible worker state.

A worker may finish internally after a disconnect if immediate cancellation is
unsafe, but its result must not be delivered to a later connection.

Immediately before READY delivery, the firmware rechecks:

```text
job connection == current connection
connection generation unchanged
CP2 transaction still valid
notifications enabled
CCCD subscribed
strict live L4 still valid
MTU sufficient
```

A stale result is discarded.

---

## Secret hygiene

The raw ML-KEM shared secret is never logged.

### Central

The Central keeps `SS_MLKEM` only for the CP2 diagnostic comparison and clears
its mutable temporary buffer in a `finally` path.

Python cannot guarantee erasure of all immutable/internal cryptographic
library copies, so the implementation only claims explicit clearing of the
mutable buffers it owns.

### Firmware

The firmware clears:

- temporary ML-KEM shared secret;
- temporary CP2 diagnostic material;
- worker state associated with obsolete CP2 operations.

No long-lived CP2 application key is retained.

# What CP2 does not yet provide

CP2 deliberately stops before the final v1 authenticated application channel.

It provides no:

- v1 transcript-bound HKDF key schedule;
- `FINISHED_C`;
- `FINISHED_P`;
- `APP_SECURE`;
- v1 application AES-256-GCM traffic;
- application P-256 ECDH;
- hybrid `SS_MLKEM || SS_ECDH`;
- application SAS;
- SMP-secret exporter;
- use of LTK/DHKey as ML-KEM KDF input.

After successful CP2 the firmware returns to:

```text
L4_SECURED
```

with:

```text
no application keys
```

This boundary was observed on real hardware.
