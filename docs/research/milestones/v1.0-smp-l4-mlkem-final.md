# v1.0 — BLE SMP Security Mode 1 Level 4 + ML-KEM-768

Status: **v1.0 COMPLETE — CP1 through CP5 PASS, including real-hardware validation on Windows PC + nRF54L15 DK.**

CP1 established and validated the BLE Security Mode 1 Level 4 foundation.
CP2 validated real ML-KEM-768 interoperability over that authenticated L4
link. CP3 added the canonical transcript, ML-KEM-only HKDF key schedule,
bidirectional FINISHED confirmation and transition to `APP_SECURE`. CP4 uses
the CP3-derived directional application keys for real bidirectional
AES-256-GCM application traffic with strict sequence-number/replay handling.
CP5 then validated the complete protocol across cold pairing, bonded
reconnections, repeated sessions, DK reboot, Central restart and bond reset.

CP2 was validated on 2026-09-09. CP3, CP4 and CP5 were software-tested and
validated on 2026-09-10. The complete v1.0 protocol has therefore been
validated end-to-end on the real target platform.

The CP1 CONFIRM_ONLY experiment remains a fail-closed observation. An actual
on-air BLE Just Works association method was **not demonstrated**. This
limitation is unchanged by later checkpoints.

The protocol implementation and lifecycle validation are complete at CP5.
Any subsequent CP6 work is treated as a separate experimental/security and
comparative evaluation of frozen v0.7 versus frozen v1.0, not as a prerequisite
for declaring the v1.0 protocol implementation complete.

## Motivation and difference from v0.7

v0.7 is an **application-level authenticated hybrid handshake**:

```text
ML-KEM-768
    +
application P-256 ECDH
    |
    v
SS_MLKEM || SS_ECDH
    |
    v
HKDF
    |
    +--> application SAS
    +--> FINISHED
    +--> AES-256-GCM
```

The v0.7 firmware runs with:

```text
CONFIG_BT_SMP=n
```

so its security properties are intentionally built above GATT.

v1.0 is a different architecture.

It is a **layered classical/PQ design**:

```text
BLE connection
      |
      v
BLE SMP Security Mode 1 Level 4
authenticated LE Secure Connections
Numeric Comparison
MITM protection
BLE Link Layer encryption
      |
      v
protected PQ GATT operations
      |
      v
ML-KEM-768
      |
      v
transcript-bound v1 key schedule        CP3
FINISHED_C / FINISHED_P
      |
      v
AES-256-GCM application channel         CP4
```

The application-level P-256 ECDH used by v0.7 is removed from the v1 path.

The v1 design therefore has:

- no application-level P-256 ECDH;
- no `SS_MLKEM || SS_ECDH` hybrid combiner;
- no application SAS;
- no `K_sas`;
- no export of the BLE SMP LTK or SMP DHKey into the application KDF.

The SMP secret and `SS_MLKEM` remain cryptographically separated.

### Security separation

| Layer | Mechanism | Post-quantum? |
|---|---|---|
| Peer authentication | BLE SMP Level 4, P-256, Numeric Comparison | no |
| BLE link encryption | BLE Link Layer using SMP-derived LTK | no |
| Application key establishment | ML-KEM-768 | yes |
| Application traffic protection | AES-256-GCM with ML-KEM-derived keys | symmetric/PQ-resistant against quantum key search at appropriate key size |

The v1 security claim must therefore remain precise:

> BLE SMP Level 4 provides classical authenticated peer association and
> link-layer protection. ML-KEM provides the post-quantum application
> key-establishment secret.

v1.0 must **not** be described as a hybrid key agreement.

## CP1 security state machine

The CP1 state progression is:

```text
DISCONNECTED
    |
    v

    |
    v

    |

```

Failure paths include:

```text

```

Any disconnect invalidates the active security context.

CP2 adds the temporary `PQ_CRYPTO_BUSY` operation after `L4_SECURED`.


## Strict Level-4 predicate

GATT permission bits alone are not treated as sufficient evidence of L4.

Every PQ-sensitive operation is additionally protected by the runtime
security gate.

The authoritative predicate requires:

```text
current tracked connection
+
security state == L4_SECURED
+
bt_conn_get_security() == BT_SECURITY_L4
+
Secure Connections flag present
+
authenticated link
+
16-byte encryption key
```

If any condition fails, PQ access fails closed.

---

## PQ GATT gating

Sensitive operations include:

- Public Key read;
- Ciphertext write;
- Secure Data access;
- Secure Data CCCD;
- Control write.

Before L4 they must fail.

After strict L4 they may become accessible.

The v1 Control characteristic rejects the legacy v0.x protocol frames so the
v0.7 hybrid handshake cannot accidentally execute inside the v1 profile.

---

## PQV1 framing — CP1 + CP2 + CP3

The v1 control protocol is versioned independently from the older v0.x
application frames.

Wire format:

```text
magic "PQV1" (4)
|| version 0x10 (1)
|| subtype (1)
|| payload_len u16be (2)
|| payload
```

### Implemented / reserved subtypes

| Subtype | Direction | Payload | Meaning |
|---|---|---|---|
| `0x01 SEC_QUERY` | C -> P | 0 B | request DK-side security attestation |
| `0x02 SEC_INFO` | P -> C | 4 B | current security state |
| `0x10 START_V1` | C -> P | `session_id(16)` | frozen CP2 TEST-ONLY ML-KEM decapsulation request |
| `0x11 READY_V1` | P -> C | `diagnostic(32)` | frozen CP2 TEST-ONLY shared-secret diagnostic |
| `0x12 FINISHED_C` | C -> P | `verify_data(32)` | CP3 Central key confirmation |
| `0x13 FINISHED_P` | P -> C | `verify_data(32)` | CP3 Peripheral key confirmation |
| `0x14 START_CP3` | C -> P | `session_id(16)` | start CP3 transcript/HKDF/FINISHED exchange |
| `0x15 READY_CP3` | P -> C | `TH0(32)` | CP3 worker completion + transcript synchronization |
| `0x7F ERROR` | P -> C | status | fail-closed protocol/security error |

### SEC_INFO

The Central accepts `SEC_INFO` only when all of the following are true:

```text
level == L4
Secure Connections == YES
authenticated == YES
encryption key size == 16
PQ GATT gate == OPEN
profile == 0x10
```

Anything weaker fails closed.

`FINISHED_C` and `FINISHED_P` remain unsupported in the frozen CP2 path but
are active only in explicit CP3 mode. `START_CP3` / `READY_CP3` are kept
separate so CP2 remains reproducible without changing its TEST-ONLY semantics.

# CP2 — ML-KEM-768 over authenticated SMP Level 4

## CP2 goal

CP2 adds one capability and proves one property:

> Run a real ML-KEM-768 encapsulation/decapsulation exchange over the already
> authenticated Level-4 link and prove that both peers independently obtain
> the same `SS_MLKEM`.

CP2 does **not** yet create the final v1 application secure channel.


## CP2 TEST-ONLY diagnostic

CP2 uses the following interoperability diagnostic:

```text
transcript_digest =
    SHA256(
        ML-KEM_public_key ||
        ML-KEM_ciphertext
    )
```

Then:

```text
diagnostic =
    HMAC-SHA256(
        key = SS_MLKEM,
        data =
            "PQ-BLE-HANDSHAKE-v1.0/CP2-DIAGNOSTIC"
            || session_id
            || transcript_digest
    )
```

Output size:

```text
32 B
```

The Central calculates its expected diagnostic from the shared secret returned
by ML-KEM encapsulation.

The nRF54L15 DK independently calculates the diagnostic from the shared secret
returned by mlkem-native decapsulation.

The Central compares the two values with a constant-time comparison.

### Important scope limitation

This construction is explicitly:

```text
TEST ONLY
```

It is **not**:

- the final v1 FINISHED;
- a production application authenticator;
- the CP3 transcript/key schedule;
- an application traffic key;
- an application SAS.

It exists only to prove CP2 ML-KEM interoperability without transmitting the
raw shared secret.

## Firmware CP2 implementation

`START_V1` is accepted only if:

- the caller is the current tracked connection;
- the live connection still satisfies strict L4;
- notifications are enabled;
- the CCCD is actually subscribed;
- the ML-KEM keypair is ready;
- the ciphertext has been fully reassembled;
- the ciphertext length is exactly 1088 B;
- no incompatible crypto operation is active;
- no stale crypto connection reference exists;
- the session identifier is exactly 16 B.

Heavy cryptographic work is not performed inside the GATT callback.

The CP2 operation uses the dedicated ML-KEM worker mode:

```text
PQ_MLKEM_JOB_V1_CP2
```

and the dedicated submission API:

```text
pq_mlkem_session_submit_v1_cp2(...)
```

The worker:

1. consumes the completed ML-KEM ciphertext;
2. performs real ML-KEM-768 decapsulation;
3. obtains a temporary local `SS_MLKEM`;
4. computes the TEST-ONLY CP2 diagnostic;
5. clears the shared secret and temporary cryptographic state;
6. returns only the encoded READY response.

---

## CP2 lifecycle

CP2 uses only a temporary crypto-busy state:

```text
L4_SECURED
    |
    | START_V1
    v
PQ_CRYPTO_BUSY
    |
    | ML-KEM decapsulation
    | + TEST-ONLY diagnostic
    v
L4_SECURED
```

Successful CP2 completion does **not** enter:

```text
WAIT_FINISHED_C
FINISHED_BUSY
APP_SECURE
DATA_BUSY
```

No application traffic keys exist at CP2.

Those are later-checkpoint concerns.

---

## Disconnect, downgrade and stale-job protection

CP2 is invalidated by:

- disconnect;
- security downgrade;
- security error;
- disabled notification subscription;
- connection-generation mismatch;
- stale originating connection;
- incompatible worker state.

A worker may finish internally after a disconnect if immediate cancellation is
unsafe, but its result must not be delivered to a later connection.

Immediately before READY delivery, the firmware rechecks:

```text
job connection == current connection
connection generation unchanged
CP2 transaction still valid
notifications enabled
CCCD subscribed
strict live L4 still valid
MTU sufficient
```

A stale result is discarded.

---

## Secret hygiene

The raw ML-KEM shared secret is never logged.

### Central

The Central keeps `SS_MLKEM` only for the CP2 diagnostic comparison and clears
its mutable temporary buffer in a `finally` path.

Python cannot guarantee erasure of all immutable/internal cryptographic
library copies, so the implementation only claims explicit clearing of the
mutable buffers it owns.

### Firmware

The firmware clears:

- temporary ML-KEM shared secret;
- temporary CP2 diagnostic material;
- worker state associated with obsolete CP2 operations.

No long-lived CP2 application key is retained.

# CP3 — transcript-bound key schedule + FINISHED

## CP3 goal

CP3 starts from the CP2 invariant:

```text
authenticated SMP Level 4
        +
matching SS_MLKEM
```

and upgrades it into an application handshake with:

```text
canonical transcript
        |
        v
HKDF-SHA256 from SS_MLKEM only
        |
        +--> K_FINISHED_C
        +--> K_FINISHED_P
        |
        v
FINISHED_C
        |
        v
FINISHED_P
        |
        v
K_APP_C2P / K_APP_P2C
        |
        v
APP_SECURE
```

CP3 does **not** yet send AES-GCM application traffic. Actual use of the
application keys remains CP4.

The v1 architecture remains layered:

```text
BLE SMP Level 4
=
classical authenticated peer association
+
BLE Link Layer encryption
```

and:

```text
SS_MLKEM
=
sole post-quantum application key-establishment input
```

The application key schedule does not use:

- the BLE SMP LTK;
- the SMP P-256 DHKey;
- application-level P-256 ECDH;
- v0.7 `SS_ECDH`;
- application SAS;
- `K_sas`.

---

## CP3 framing

CP2 remains frozen:

```text
0x10 START_V1
0x11 READY_V1
```

CP3 activates:

```text
0x12 FINISHED_C
0x13 FINISHED_P
0x14 START_CP3
0x15 READY_CP3
```

### START_CP3

Payload:

```text
session_id = 16 fresh random bytes
```

Frame size:

```text
8-B PQV1 header + 16-B session_id = 24 B
```

### READY_CP3

Payload:

```text
TH0 = 32 B
```

Frame size:

```text
8-B PQV1 header + 32-B TH0 = 40 B
```

`READY_CP3` is not an authenticator. It confirms worker completion and allows
the Central to verify that both peers constructed the same canonical
transcript.

### FINISHED_C / FINISHED_P

Each FINISHED contains:

```text
verify_data = 32 B
```

for a total frame size of:

```text
40 B
```

## Canonical CP3 transcript

Both Python and C use exactly:

```text
T0 =
    "PQ-BLE-HANDSHAKE-v1.0/CP3-TRANSCRIPT"
    ||
    SEC_INFO_FRAME
    ||
    MLKEM_PUBLIC_KEY
    ||
    MLKEM_CIPHERTEXT
    ||
    START_CP3_FRAME
```

with:

```text
SEC_INFO_FRAME      = 12 B canonical PQV1 frame
MLKEM_PUBLIC_KEY    = 1184 B
MLKEM_CIPHERTEXT    = 1088 B
START_CP3_FRAME     = 24 B
```

Then:

```text
TH0 = SHA256(T0)
```

The Central uses the exact second strict `SEC_INFO` received immediately before
`START_CP3`.

The DK reconstructs the canonical `SEC_INFO` from its live strict-L4 security
state when accepting `START_CP3`.

A `READY_CP3` transcript mismatch fails closed.

## CP3 key schedule

The sole secret input is:

```text
IKM = SS_MLKEM
```

with:

```text
SS_MLKEM = 32 B
```

### Extract

```text
PRK =
    HKDF-Extract(
        salt = TH0,
        IKM  = SS_MLKEM
    )
```

For SHA-256 this is implemented as:

```text
PRK = HMAC-SHA256(TH0, SS_MLKEM)
```

### Directional FINISHED keys

```text
K_FINISHED_C =
    HKDF-Expand(
        PRK,
        "PQ-BLE-HANDSHAKE-v1.0/FINISHED-C" || TH0,
        32
    )
```

```text
K_FINISHED_P =
    HKDF-Expand(
        PRK,
        "PQ-BLE-HANDSHAKE-v1.0/FINISHED-P" || TH0,
        32
    )
```

Since `L = 32`, HKDF-Expand requires exactly one SHA-256 output block.

---

## FINISHED_C

The Central computes:

```text
VERIFY_C =
    HMAC-SHA256(
        K_FINISHED_C,
        "PQ-BLE-HANDSHAKE-v1.0/VERIFY-C" || TH0
    )
```

and sends:

```text
FINISHED_C(VERIFY_C)
```

The DK verifies the 32-byte value with a constant-time comparison.

A wrong `FINISHED_C`:

- never produces `FINISHED_P`;
- never creates an active application session;
- never enters `APP_SECURE`;
- clears the CP3 handshake material.

After valid `FINISHED_C`:

```text
TH1 =
    SHA256(
        TH0 ||
        exact FINISHED_C frame
    )
```

---

## FINISHED_P

The DK computes:

```text
VERIFY_P =
    HMAC-SHA256(
        K_FINISHED_P,
        "PQ-BLE-HANDSHAKE-v1.0/VERIFY-P" || TH1
    )
```

and sends:

```text
FINISHED_P(VERIFY_P)
```

The Central verifies the value in constant time.

After valid `FINISHED_P`:

```text
TH2 =
    SHA256(
        TH1 ||
        exact FINISHED_P frame
    )
```

## CP3 application keys

Only after the valid bidirectional FINISHED exchange:

```text
K_APP_C2P =
    HKDF-Expand(
        PRK,
        "PQ-BLE-HANDSHAKE-v1.0/APP-C2P" || TH2,
        32
    )
```

```text
K_APP_P2C =
    HKDF-Expand(
        PRK,
        "PQ-BLE-HANDSHAKE-v1.0/APP-P2C" || TH2,
        32
    )
```

The values are never logged.

CP3 stores them only for the live application session and transitions to:

```text
APP_SECURE
```

No CP3 code sends AES-GCM application PING/PONG messages. That remains CP4.

## CP3 firmware lifecycle

The CP3 firmware state machine is:

```text
L4_SECURED
    |
    | START_CP3
    v
CP3_CRYPTO_BUSY
    |
    | ML-KEM decapsulation
    | + transcript
    | + HKDF
    v
WAIT_FINISHED_C
    |
    | valid FINISHED_C
    v
FINISHED_P_BUSY
    |
    | FINISHED_P successfully queued
    v
APP_SECURE
```

`START_CP3` is accepted only when:

- the caller is the current tracked BLE connection;
- strict live L4 is still valid;
- the connection generation is current;
- notifications are enabled;
- the Secure Data CCCD is subscribed;
- the ML-KEM keypair is ready;
- the complete 1088-B ciphertext is ready;
- no CP2/CP3 or incompatible crypto job is active;
- there is no stale job connection;
- the `session_id` is exactly 16 B;
- the MTU can carry the required 40-B notification frame.

CP3 uses dedicated worker modes:

```text
PQ_MLKEM_JOB_V1_CP3
PQ_MLKEM_JOB_V1_CP3_FINISHED_C
```

and dedicated APIs for start, FINISHED processing, commit and reset.

Application keys are kept pending until `FINISHED_P` is successfully queued.
Only then is the session committed as `APP_SECURE`.

## CP3 fail-closed lifecycle

CP3 fails closed on:

- pre-L4 START;
- stale caller;
- incomplete ciphertext;
- notifications disabled;
- CCCD unsubscribed;
- CP2 active;
- crypto worker busy;
- stale job reference;
- unavailable ML-KEM keypair;
- malformed START;
- insufficient MTU;
- FINISHED before readiness;
- duplicate START;
- duplicate FINISHED;
- wrong-role FINISHED;
- wrong `FINISHED_C`;
- wrong `FINISHED_P`;
- worker crypto failure;
- PSA hash/MAC failure;
- READY notification failure;
- FINISHED notification failure;
- disconnect;
- connection replacement;
- security downgrade;
- security error;
- stale connection generation;
- CCCD disable during handshake;
- absolute CP3 timeout.

A stale worker result is never allowed to create application keys for a later
connection.

## CP3 secret lifetime

### Central

Temporary handshake secrets are cleared on success and every failure path.

After successful `FINISHED_P` verification:

```text
SS_MLKEM        cleared
PRK             cleared
K_FINISHED_C    cleared
K_FINISHED_P    cleared
transcript hash cleared
```

The live session retains:

```text
K_APP_C2P
K_APP_P2C
```

until disconnect/session invalidation.

Python cannot guarantee erasure of immutable copies internal to Python or
liboqs; the implementation claims only best-effort clearing of mutable buffers
it directly owns.

### DK

After ML-KEM decapsulation and schedule setup:

```text
SS_MLKEM cleared
```

After successful FINISHED processing and application-key creation:

```text
CP3 handshake secrets cleared
```

On disconnect, failure or security invalidation, CP3 application keys are also
invalidated.

No secret or traffic-key value is printed in the logs.

# CP4 — bidirectional AES-256-GCM application data

## CP4 goal

CP4 starts from the validated CP3 invariant:

```text
authenticated SMP Level 4
        +
transcript-bound ML-KEM key schedule
        +
FINISHED_C / FINISHED_P verified
        +
APP_SECURE
        +
K_APP_C2P / K_APP_P2C
```

and activates the real v1 application-data plane:

```text
Central
    |
    | AES-256-GCM PING using K_APP_C2P
    v
nRF54L15 DK
    |
    | authenticate + decrypt
    |
    | AES-256-GCM PONG using K_APP_P2C
    v
Central
    |
    | authenticate + decrypt
    v
APP_SECURE
```

CP4 introduces no new key exchange and does not alter the validated CP3
transcript, FINISHED messages or application-key values.

---

## CP4 wire subtypes

```text
0x20 APP_C2P
0x21 APP_P2C
```

Direction is protocol-significant:

```text
APP_C2P = Central -> Peripheral
APP_P2C = Peripheral -> Central
```

The CP4 positive flow uses:

```text
0x01 PING
0x02 PONG
```

Each PING contains a fresh 16-byte random challenge. The matching PONG returns
the exact same 16-byte plaintext after authenticated decryption/encryption.

Challenge values are never logged.

---

## CP4 frame format

CP4 retains the existing PQV1 outer header:

```text
magic          4 B = "PQV1"
version        1 B = 0x10
subtype        1 B
payload_len    2 B big endian
```

The CP4 application payload is:

```text
seq            8 B big endian
msg_type       1 B
plaintext_len  2 B big endian
ciphertext     N B
tag            16 B
```

Complete frame:

```text
PQV1(4)
| version(1)
| subtype(1)
| payload_len(2BE)
| seq(8BE)
| msg_type(1)
| plaintext_len(2BE)
| ciphertext(N)
| tag(16)
```

For the mandatory 16-byte PING/PONG:

```text
PQV1 header              8 B
sequence                 8 B
message type             1 B
plaintext length         2 B
ciphertext              16 B
GCM tag                 16 B
----------------------------
total                    51 B
```

ATT requires:

```text
51 B frame + 3 B ATT overhead = minimum ATT MTU 54
```

The validated hardware sessions negotiated:

```text
MTU = 247
```

so the CP4 51-byte application frame fits without application fragmentation.

---

## CP4 directional IV derivation

CP4 derives deterministic 96-bit IV bases from the already session-specific
CP3 application keys.

```text
IV_C2P =
    HKDF-Expand(
        K_APP_C2P,
        "PQ-BLE-HANDSHAKE-v1.0/IV-C2P" || session_id,
        12
    )
```

```text
IV_P2C =
    HKDF-Expand(
        K_APP_P2C,
        "PQ-BLE-HANDSHAKE-v1.0/IV-P2C" || session_id,
        12
    )
```

This derivation does not modify the CP3 KDF and does not combine the
application keys with SMP material.

IV values are never logged.

---

## CP4 nonce construction

For sequence number `seq`:

```text
SEQ96 =
    0x00000000
    ||
    seq_u64be
```

Then:

```text
nonce =
    IV_base XOR SEQ96
```

so:

```text
nonce_C2P(seq) =
    IV_C2P XOR (zero32 || seq64be)
```

```text
nonce_P2C(seq) =
    IV_P2C XOR (zero32 || seq64be)
```

This yields a deterministic 96-bit nonce tied to both direction and sequence.

`UINT64_MAX` is reserved against sequence wrap/reuse.

---

## CP4 AAD

The domain-separation label is:

```text
"PQ-BLE-HANDSHAKE-v1.0/CP4-AAD"
```

For each application frame:

```text
AAD =
    "PQ-BLE-HANDSHAKE-v1.0/CP4-AAD"
    ||
    session_id
    ||
    exact_PQV1_header
    ||
    seq_u64be
    ||
    msg_type
    ||
    plaintext_len_u16be
```

where `exact_PQV1_header` is the transmitted 8-byte header:

```text
"PQV1"
|| 0x10
|| subtype
|| payload_len_u16be
```

The AAD therefore binds:

- CP4 domain;
- CP3 session;
- v1 version;
- application direction;
- exact outer payload length;
- sequence number;
- application message type;
- plaintext length.

## CP4 AES-GCM protection

CP4 uses:

```text
AES-256-GCM
key size = 32 B
nonce    = 12 B
tag      = 16 B
```

Direction:

```text
Central -> DK
    K_APP_C2P
    IV_C2P

DK -> Central
    K_APP_P2C
    IV_P2C
```

No application P-256 ECDH, `SS_ECDH`, SAS, SMP LTK or SMP DHKey is introduced
into CP4.

The v1 separation remains:

```text
SMP L4
    = classical authenticated BLE link + Link Layer encryption

ML-KEM + CP3
    = post-quantum application key establishment + key confirmation

CP4
    = authenticated application data using CP3-derived AES-256-GCM keys
```

## CP4 sequence/replay semantics

Logical counters:

```text
Central:
    tx_c2p
    rx_p2c

DK:
    rx_c2p
    tx_p2c
```

The validated CP4 positive run performs exactly two rounds:

```text
round 0:
    C2P seq = 0
    P2C seq = 0

round 1:
    C2P seq = 1
    P2C seq = 1
```

Receiver acceptance is strict:

```text
received_seq == expected_rx_seq
```

There is:

- no replay window;
- no duplicate acceptance;
- no skipped sequence acceptance;
- no out-of-order acceptance.

Replay or sequence failure invalidates the live application session.

The Central consumes its transmit sequence before transport so the same
key/nonce pair cannot be reused after a send failure.

On the DK, application counter advancement is committed only after successful
C2P authentication, PONG generation, live-session checks and successful
P2C notification queueing. Failure invalidates the session instead of
continuing with ambiguous counter state.

---

## CP4 application-session lifecycle

CP4 is accepted only from an existing CP3:

```text
APP_SECURE
```

The same BLE connection owns:

```text
session_id
K_APP_C2P
K_APP_P2C
directional IV bases
application counters
```

The positive data path is conceptually:

```text
APP_SECURE
    |
    | APP_C2P
    v
DATA_BUSY
    |
    | authenticate/decrypt PING
    | encrypt PONG
    | notify APP_P2C
    v
APP_SECURE
```

Fatal application-data failures invalidate the session and clear application
keys.

The software coverage includes fail-closed handling for replay/ordering,
authentication/tag failure, wrong direction, malformed data, stale connection
state, session invalidation and sequence exhaustion.

# CP5 — lifecycle and multi-session validation

## CP5 goal

CP5 does not introduce a new cryptographic protocol stage.

Its purpose is to validate that the complete CP1-CP4 protocol behaves correctly
across multiple BLE connection and application-session lifecycles.

The central invariant is:

```text
BLE bonding may persist
        |
        v
new BLE connection
        |
        v
new ML-KEM exchange
        |
        v
new CP3 application session
        |
        v
new K_APP_C2P / K_APP_P2C
        |
        v
CP4 counters restart from zero
```

A persisted SMP bond must never imply persisted application-session state.

In particular, a new connection must not intentionally reuse:

```text
SS_MLKEM
PRK
K_FINISHED_C
K_FINISHED_P
K_APP_C2P
K_APP_P2C
IV_C2P
IV_P2C
CP4 sequence counters
pending CP4 transfer state
```

## CP5 production fix

The CP5 audit found one concrete lifecycle issue.

A retired CP4 worker could complete after a reconnection and leave the shared
transfer slot occupied.

The firmware was corrected with a small lifecycle fix in `main.c` so that
retired CP4 work releases the transfer slot correctly even when completion
occurs after reconnection.

This was a lifecycle/resource-ownership fix only.

It did **not** change:

- the v1 cryptographic design;
- CP3 transcript semantics;
- FINISHED semantics;
- application-key derivation;
- CP4 frame format;
- CP4 IV/nonce construction;
- CP4 AAD;
- AES-256-GCM semantics.
