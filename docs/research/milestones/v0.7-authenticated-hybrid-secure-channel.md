# v0.7 — Authenticated hybrid ML-KEM-768 + P-256 secure channel

Status: **COMPLETE** — software, pristine-build, positive physical nRF54L15 DK
E2E validation, authenticated bidirectional application traffic, and CP4
negative/security validation completed.

This milestone extends the frozen v0.6 authenticated bidirectional secure
channel with a genuine application-layer hybrid key establishment:

- ML-KEM-768 for post-quantum key establishment;
- NIST P-256 ECDH for a classical component;
- transcript-bound hybrid HKDF-SHA256;
- six-digit SAS Numeric Comparison;
- bidirectional FINISHED key confirmation;
- direction-separated AES-256-GCM application traffic;
- replay protection with independent sequence spaces;
- fail-closed state transitions and epoch/generation cancellation.

Bluetooth SMP remains disabled. The P-256 ECDH component described here is
part of the application protocol and is not BLE SMP ECDH.

---

## Architecture

The validated physical configuration is:

| Component | Configuration |
|---|---|
| Peripheral | Nordic nRF54L15 DK |
| Firmware | nRF Connect SDK 3.0.0 / Zephyr 4.0.99 |
| Target | `nrf54l15dk/nrf54l15/cpuapp` |
| Compiler profile | C99, optimized firmware build |
| Central | Windows PC, Python + Bleak |
| PQ implementation on Central | liboqs / liboqs-python, ML-KEM-768 |
| PQ implementation on DK | mlkem-native v2.0.0 integration |
| Classical hybrid component | NIST P-256 / secp256r1 |
| Firmware crypto API | PSA Crypto / Cracen-backed P-256 support |
| Application AEAD | AES-256-GCM |
| BLE SMP | `CONFIG_BT_SMP=n` |
| Crypto worker stack | 28,672 B |

The GATT service and characteristic layout are unchanged from earlier
milestones. No new characteristic was added for v0.7.

Heavy cryptographic work is never executed inside a GATT callback. ML-KEM
decapsulation, P-256 ECDH, transcript hashing, hybrid key derivation,
FINISHED processing, traffic-key derivation, and AES-GCM application processing
run on the existing dedicated crypto worker.

A separate Phase 7 epoch invalidates stale authenticated material and running
results. The BLE layer also retains the existing connection-generation checks,
so a result produced for an old connection cannot be delivered to a replacement
peer.

## P-256 representation

The curve is NIST P-256 / secp256r1.

```text
private scalar: 32 bytes
public key:     65 bytes
                0x04 || X(32) || Y(32)
ECDH secret:    32 bytes
```

Both endpoints validate the exact SEC1 uncompressed representation before the
peer key is used.

---

## Canonical v0.7 transcript

The protocol domain is:

```text
PQ-BLE-HANDSHAKE-v0.7
```

The canonical transcript is exactly **2,457 bytes** and contains eight ordered
length-prefixed fields:

```text
u16be(21)   || "PQ-BLE-HANDSHAKE-v0.7"
u16be(1)    || 0x01                        # Central role
u16be(1)    || 0x02                        # Peripheral role
u16be(16)   || session_id
u16be(1184) || ML-KEM-768 public_key
u16be(1088) || ML-KEM-768 ciphertext
u16be(65)   || Central_P256_public_key
u16be(65)   || Peripheral_P256_public_key
```

Both endpoints independently compute:

```text
transcript_hash = SHA-256(canonical_transcript)
```

The DK hashes the canonical serialization without requiring the Central to send
a transcript hash as a source of truth.

## Hybrid IKM and key schedule

The two shared secrets are mandatory. There is no fallback to a single
component.

```text
hybrid_IKM =
    u16be(32) || SS_MLKEM ||
    u16be(32) || SS_ECDH
```

Total hybrid IKM size:

```text
68 bytes
```

The v0.7 key schedule is:

```text
key_block = HKDF-SHA256(
    IKM  = hybrid_IKM,
    salt = transcript_hash,
    info = b"PQ-BLE-HANDSHAKE-v0.7/hybrid-key-schedule",
    L    = 128
)

K_app        = key_block[0:32]
K_sas        = key_block[32:64]
K_finished_c = key_block[64:96]
K_finished_p = key_block[96:128]
```

The raw ML-KEM and ECDH shared secrets are wiped after the hybrid schedule has
been derived. Temporary hybrid IKM and temporary key structures are also
cleared.

`K_sas` is not retained after SAS generation.

## SAS Numeric Comparison

The SAS is derived independently by both endpoints:

```text
sas_mac = HMAC-SHA256(
    K_sas,
    b"PQ-BLE-HANDSHAKE-v0.7/SAS" || transcript_hash
)

sas = int.from_bytes(sas_mac, "big") mod 1_000_000
```

The displayed value is always six decimal digits, including leading zeroes.

The SAS is not transmitted as the source of truth. The Central displays its
locally computed value and the Peripheral displays its independently computed
value through the serial console.

Normal authenticated mode requires explicit human confirmation and defaults to
rejection.

One observed positive physical run produced the matching value:

```text
Central:    841049
Peripheral: 841049
```

Other matching SAS values were observed across independent runs, as expected
from fresh session and ephemeral key material.

## FINISHED key confirmation

After explicit SAS acceptance:

```text
FINISHED_C = HMAC-SHA256(
    K_finished_c,
    b"PQ-BLE-HANDSHAKE-v0.7/FINISHED/C" || transcript_hash
)

FINISHED_P = HMAC-SHA256(
    K_finished_p,
    b"PQ-BLE-HANDSHAKE-v0.7/FINISHED/P" || transcript_hash
)
```

Both values are the full 32-byte HMAC output.

The Peripheral verifies `FINISHED_C` with the firmware constant-time comparison
helper. The Central verifies `FINISHED_P` using `hmac.compare_digest`.

Application traffic is not enabled merely because `FINISHED_C` verifies.

The Peripheral:

1. verifies `FINISHED_C`;
2. generates `FINISHED_P`;
3. derives pending direction-separated traffic keys;
4. clears `K_app`, FINISHED keys, and transcript material no longer needed;
5. queues `FINISHED_P` successfully to the live originating BLE connection;
6. only then promotes the pending traffic keys to the authenticated application
   state.

This prevents application activation if the connection fails between
FINISHED verification and FINISHED delivery.

## Direction-separated v0.7 traffic keys

`K_app` is a traffic-key root and is never used directly as the AES key for
v0.7 application traffic.

```text
K_c2p = HMAC-SHA256(
    K_app,
    b"PQ-BLE-TRAFFIC-v0.7/CENTRAL-TO-PERIPHERAL"
)

K_p2c = HMAC-SHA256(
    K_app,
    b"PQ-BLE-TRAFFIC-v0.7/PERIPHERAL-TO-CENTRAL"
)
```

The two directions have independent keys and independent sequence spaces.

## PQS7 frame protocol

The generic v0.7 handshake frame is:

```text
"PQS7" (4) ||
version=0x07 (1) ||
subtype (1) ||
payload_len_be16 (2) ||
payload
```

| Subtype | Value | Direction | Payload | Total |
|---|---:|---|---:|---:|
| `START7` | `0x01` | C→P Control | `sid(16) + C_P256(65)` | 89 B |
| `READY7_CP2` | `0x02` | P→C Notify | `P_P256(65) + diagnostic(32)` | 105 B |
| `START7_AUTH` | `0x03` | C→P Control | `sid(16) + C_P256(65)` | 89 B |
| `READY7_AUTH` | `0x04` | P→C Notify | `P_P256(65)` | 73 B |
| `FINISHED_C` | `0x05` | C→P Control | 32 B | 40 B |
| `FINISHED_P` | `0x06` | P→C Notify | 32 B | 40 B |
| `ERROR` | `0x7f` | P→C Notify | status byte | 9 B |

The existing ML-KEM ciphertext characteristic and application fragmentation
format are unchanged.

## Peripheral v0.7 state machine

The authenticated-hybrid path uses a state machine independent from Phase 5/6:

```text
IDLE
  -> CRYPTO_BUSY
  -> WAIT_FINISHED_C
  -> FINISHED_BUSY
  -> AUTHENTICATED
  -> DATA_BUSY
  -> AUTHENTICATED
```

Disconnect, CCCD disable, stale epoch, stale generation, failed FINISHED
delivery, or explicit reset clears retained v0.7 session material.

Pre-authenticated Secure Data writes are rejected.

## CP4 physical negative validation

All seven CP4 security cases were exercised against the physical DK.

### 1. SAS rejection

Command:

```powershell
python -m src.central.main --phase7-auth-hybrid \
  --phase7-negative-test-only sas-reject
```

Validated property:

- SAS is independently computed;
- the Central rejects deterministically;
- `FINISHED_C` is not sent;
- the Peripheral remains in `WAIT_FINISHED_C`;
- application Secure Data remains blocked;
- no authenticated application state is reached.

### 2. Tampered FINISHED_C

Command:

```powershell
python -m src.central.main --phase7-auth-hybrid \
  --phase7-negative-test-only finished-c
```

Validated property:

- exactly one FINISHED_C bit is changed;
- the Peripheral logs `Phase 7 FINISHED_C verification: FAIL`;
- PQS7 authentication failure status `0x06` is returned;
- a valid FINISHED_P is not accepted as success;
- the application session remains unavailable.

### 3. Pre-authenticated Secure Data

Command:

```powershell
python -m src.central.main --phase7-auth-hybrid \
  --phase7-negative-test-only pre-auth
```

Validated property:

- a valid seq=0 application probe is attempted while the Peripheral is in
  `WAIT_FINISHED_C`;
- the write is rejected;
- no application response is emitted;
- after normal SAS/FINISHED authentication, the original seq=0 wire remains
  valid;
- valid seq=0, seq=1, and seq=2 traffic then succeeds.

Therefore a rejected pre-auth probe does not consume replay/sequence state.

### 4. C→P AES-GCM tag tamper

Command:

```powershell
python -m src.central.main --phase7-auth-hybrid \
  --phase7-negative-test-only c2p-tamper
```

Validated property:

- a valid C→P seq=0 wire is copied;
- exactly one GCM-tag bit is changed;
- the Peripheral rejects it with authentication status `0x06`;
- receive sequence state does not advance;
- the untouched original seq=0 wire is then accepted;
- seq=1 and seq=2 also succeed.

### 5. C→P exact replay

Command:

```powershell
python -m src.central.main --phase7-auth-hybrid \
  --phase7-negative-test-only c2p-replay
```

Validated property:

- the first seq=0 request succeeds;
- the exact authenticated wire is replayed;
- the Peripheral rejects it as replay/out-of-order with status `0x04`;
- no duplicate PONG success response is produced;
- seq=1 and seq=2 continue to work;
- the authenticated session itself remains usable.

### 6. P→C local tag tamper

Command:

```powershell
python -m src.central.main --phase7-auth-hybrid \
  --phase7-negative-test-only p2c-tamper
```

The mutation is deliberately receiver-local on an actual BLE response; the
firmware is not modified to emit a malformed packet.

Validated property:

- a real P→C response is received;
- one tag bit is changed in a local copy;
- the Central rejects the modified copy;
- Central receive state does not advance;
- the untouched real response is still accepted;
- later round trips succeed.

### 7. P→C local replay

Command:

```powershell
python -m src.central.main --phase7-auth-hybrid \
  --phase7-negative-test-only p2c-replay
```

Validated property:

- a real P→C seq=0 response is accepted once;
- the same received wire is replayed locally;
- the Central rejects it before treating it as fresh application data;
- receive count does not advance on rejection;
- seq=1 and seq=2 remain valid.

No CP4 negative path released unauthorized application data.

## Security properties demonstrated by v0.7

The implemented and experimentally validated properties are:

- post-quantum ML-KEM-768 contribution to the application key schedule;
- independent classical P-256 ECDH contribution;
- mandatory hybrid combiner with no one-component fallback;
- transcript binding of identities/roles, session identifier, ML-KEM material,
  and both P-256 public keys;
- human MITM detection mechanism through SAS Numeric Comparison;
- explicit bidirectional key confirmation through FINISHED_C/FINISHED_P;
- application activation only after successful confirmation;
- AES-256-GCM authenticity and confidentiality;
- session binding in AAD;
- sender-role binding in AAD;
- message-type binding in AAD;
- direction-separated traffic keys;
- independent monotonic sequence spaces;
- replay rejection;
- no receive-state advance after failed AEAD authentication;
- pre-authenticated application-data rejection;
- stale-session/connection result cancellation;
- secret cleanup after state transitions.

## Scope and limitations

This remains a research prototype.

The following are intentionally outside the completed v0.7 milestone:

- BLE SMP/pairing as a requirement for the application protocol;
- ML-DSA or certificate-based non-interactive endpoint authentication;
- persistent DK session resumption for the hybrid channel;
- formal protocol verification;
- physical side-channel evaluation;
- fault-injection evaluation;
- energy-consumption benchmark;
- production UI for SAS display;
- production hardening/certification.

`CONFIG_BT_SMP=n` is intentional for this experiment: the measured security
properties belong to the application-layer PQ/hybrid protocol rather than to
BLE link-layer pairing.
