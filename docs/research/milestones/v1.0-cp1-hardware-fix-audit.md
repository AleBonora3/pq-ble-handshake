## Confirmed defects

1. **Competing initiation order.** The original DK called
   `bt_conn_set_security(L4)` unconditionally from `connected()`. The Central
   connected, performed four probes, and only then registered its custom
   pairing handler. The submitted logs demonstrate SMP and NC starting in
   `pre-l4-only`; its claim of "no pairing attempted" described only the PC.
   This ordering exists independently of Python deferral correctness.
2. **Unowned pending human decision.** The original synchronous handler did
   obtain a deferral and used `run_coroutine_threadsafe` correctly to leave
   the WinRT thread. However, it never cancelled or drained its `decisions`
   after PairAsync ended. A late operator response could still call Accept
   on an ended ceremony. Exceptions were merely logged. Blocking console
   `input()` in the default executor could also keep Python alive after abort.
3. **Unsound and racy negative oracle.** Every `paired=False` result was
   called an expected rejection, including generic FAILED with no human NC.
   The runner then checked `is_connected` once and probed the same connection;
   a deferred Windows disconnect raced those probes. Conversely, reconnect
   returning False was treated as PASS without obtaining fresh evidence.
4. **Runtime gate gaps.** CCCD relied only on permissions, despite the
   application requiring callback-tracked L4. The security gate sampled its
   tracked state before releasing the lock and checking live state, without
   a generation. SEC_INFO notification needed an explicit final runtime
   check because the value characteristic is write-only.
5. **Firmware decision lifecycle.** Simultaneous accept/reject buttons
   accepted first; timeout work could consume a newer pending challenge;
   security_changed(error) did not itself release pending consent. Pending
   passkeys were read outside their state lock. These are independently
   testable defects, not proven causes of the reported Windows failure.

## Strong findings and limits of diagnosis

The DK reached Numeric Comparison, which is strong evidence that the
association model and basic ECC/SMP configuration were working. The early
DK Security Request is the leading explanation for Windows reaching pairing
before this application's custom ceremony exists. Removing that initiator
addresses a demonstrated ordering problem, without pretending that the
generic failure status proves the OS's internal reason.

The original callback was **not** an `async def` passed directly to WinRT;
its two-argument signature, synchronous GetDeferral, asynchronous decision,
Accept-before-Complete ordering and named two-argument overload were correct.
Microsoft documents the minimum-protection overload and deferrals for user
interaction; its official sample uses a deferral for ConfirmPinMatch.
[PairAsync](https://learn.microsoft.com/en-us/uwp/api/windows.devices.enumeration.deviceinformationcustompairing.pairasync),
[GetDeferral](https://learn.microsoft.com/en-us/uwp/api/windows.devices.enumeration.devicepairingrequestedeventargs.getdeferral),
[Microsoft custom-pairing sample](https://github.com/microsoft/Windows-universal-samples/blob/main/Samples/DeviceEnumerationAndPairing/cs/Scenario9_CustomPairDevice.xaml.cs)

Installed versions inspected: Bleak 3.0.2, winrt-runtime and
winrt-Windows.Devices.Enumeration 3.2.1. Their type information confirms
`pair_with_protection_level_async(kind, protection)`, synchronous TypedEventHandler,
`CONFIRM_PIN_MATCH=8`, `CONFIRM_ONLY=1`, authenticated protection=3 and encryption=2.
Device identity is obtained in the same way as installed Bleak: fresh
DeviceInformation from its requester's ID, not a name/address-type guess.

**Original failure hypotheses (not proven by the later successful run):** Windows/driver behavior when security is
requested before the custom API, Windows-triggered pairing on protected
access, other applications/OS consent UI, and asymmetric stale bonds. The
old logs do not distinguish them. In particular, enum `BT_SECURITY_ERR_UNSPECIFIED`
is application error **9**, not proof of SMP wire reason 0x09; the pinned
translation maps wire UNSPECIFIED and unrecognized reasons to it. Preserve
the stack's `pairing failed (peer reason 0x...)` line if emitted.

## Pinned source validation and resulting design

Primary authority: local `C:/ncs/v3.0.0/zephyr`, verified by
`git describe` as `v4.0.99-ncs1`, plus sdk-nrf v3.0.0 DK library.

| Pinned source/function | Finding and implication |
|---|---|
| `host/Kconfig`, `smp.c:remote_sec_level_reachable` | SC_ONLY forces L4 requirements for incoming pairing too: SC, 16-byte key, authenticated association; Just Works fails. Cold peers can safely wait for Central-initiated SMP. |
| `smp.c:get_io_capa`, `get_auth` | Display + confirm selects DisplayYesNo; ENFORCE_MITM sets MITM when IO permits. No fixed passkey is used. |
| `smp.c:smp_send_security_req`, `conn.c:bt_conn_set_security` | Peripheral request actually starts SMP; it is now issued only for a stored bond. Automatic GATT security re-establishment is disabled so initiation has one owner. |
| `smp.c:smp_pairing_accept_query` | An application may allow the incoming attempt before NC; this is not human authentication. One attempt per connection prevents an old decision being consumed by a new SMP attempt. |
| `hci_core.c:update_sec_level` | L4 implies authenticated key + SC + 16 bytes. There is no separate public authenticated flag in this version; live L4 supplies that evidence. |
| `conn.c:bt_conn_get_info`, `bt_conn_enc_key_size` | Public SC flag, live state/level and key length are available. Key size is zero when encryption is off. The gate checks these plus the tracked current generation under its state lock. |
| `smp.c:bt_smp_auth_passkey_confirm`, `bt_smp_auth_cancel` | Confirmation/cancellation consumes SMP_FLAG_USER. Refcounts and one-attempt-per-connection prevent stale pointers/decisions from authenticating a future pairing. Bluetooth mutation calls occur outside the state mutex. |
| `smp.c:security_err_get`, `smp_pairing_failed`, `smp_pairing_complete` | Error 9 is lossy; cancel, security_changed and pairing_failed may occur in succession. Cleanup is idempotent. Stack failures may be followed by disconnect; the runner must not assume a live transport. |
| `gatt.c:bt_gatt_check_perm`, `gatt.h:_bt_gatt_ccc` | AUTHEN and LESC flags plus the runtime gate protect values; CCCD cfg_write/read are now gated too. `is_host_managed_ccc` recognizes the original write function pointer, so it is preserved for settings/restoration. |
| `gatt.c:bt_gatt_notify_cb` | The write-only Secure Data value has no read-encryption permission mask. SEC_INFO must explicitly recheck the runtime gate before notifying. |
| `smp.c:smp_pairing_complete`, settings | Keys are stored before pairing_complete; settings load after bt_enable and before advertising is correct. Existing authenticated SC bonds restore L4 without NC; stale bonds must be cleared on both peers. |
| sdk-nrf `dk_buttons_and_leds.c:buttons_scan_fn` | Button callbacks run on the system workqueue. Arming is placed on that queue, requires released buttons, and a generation-bound decision consumes one pending reference. Reject wins a simultaneous press. |

The shared call graph was also checked: `main.c` sensitive callbacks and
worker completion, `mlkem_session` startup/public-key/reset functions,
PSA initialization and clear helpers, Python fragmentation/encapsulation,
transport notification and unpair methods, PQV1 encoder/parser/constants,

Legacy control is rejected before any v0.x handshake entry; Secure Data

## Negative security oracle

The automated NC verdict requires an actual six-digit NC ceremony and
explicit PC rejection. No Accept is called. Generic FAILED then has local
rejection provenance; FAILED without that evidence remains inconclusive.
After PC acceptance, even AUTHENTICATION_FAILURE is insufficient to prove a
DK button rejection rather than a later key-distribution failure. Such a
DK-only run requires UART history, rather than an automatic PASS.

The CONFIRM_ONLY test now requests minimum ENCRYPTION, so it offers an
unauthenticated path instead of requiring authentication in its own call.
A specific security refusal qualifies; generic FAILED qualifies only after
that ceremony was actually received and accepted. PairingKinds names a
Windows ceremony, not an on-air IO-capability override. Radio-level Just
Works claims need matching peripheral/trace evidence.
[DevicePairingKinds](https://learn.microsoft.com/en-us/uwp/api/windows.devices.enumeration.devicepairingkinds)

The 2026-09-09 reporting change adds a typed inconclusive result while
preserving those evidence checks and the nonzero exit. Generic FAILED with
no callback now prints `NEGATIVE TEST: INCONCLUSIVE (just-works)` and
`CONFIRM_ONLY FAIL-CLOSED: INCONCLUSIVE (insufficient automated evidence)`;
it no longer logs the entire CP1 foundation as failed. Only a supported
rejection followed by the existing no-bond/no-notification/four-fresh-denials
checks prints `CONFIRM_ONLY FAIL-CLOSED: PASS`. Both report
`RADIO-LEVEL JUST WORKS: NOT DEMONSTRATED`. Security violations still FAIL.

For either supported rejection, verify no notification or Windows bond,
retire the old GATT session, wait for the original peer's advertisement,
reconnect it with a new client, recheck the bond state, and require four
security denials. No bond is deleted to manufacture an unpaired outcome.
A successful operation/bond/notification fails; missing verification evidence
is inconclusive and exits nonzero. The old connection's expected disconnect
is logged as part of security rejection rather than "Unexpected disconnect".

The full physical oracle includes the DK history: **no authenticated L4 and
no gate OPEN at any time**, in addition to no successful PQ access. Four
GATT samples or a final Windows store snapshot alone cannot prove history.
This limitation is explicit in the test output and retest procedure.
