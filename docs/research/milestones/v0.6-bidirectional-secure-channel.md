# v0.6 — Authenticated Bidirectional Secure Channel

**Status:** COMPLETE  
**Date:** 2026-09-05  
**Target:** nRF54L15 DK (`nrf54l15dk/nrf54l15/cpuapp`)  
**NCS:** 3.0.0  
**Zephyr:** 4.0.99  
**Central:** Windows + Python + Bleak + liboqs-python  
**Peripheral:** nRF54L15 DK + Zephyr/NCS + mlkem-native  
**BLE role:** PC Central ↔ nRF54L15 Peripheral  

---

## 1. Objective

v0.6 extends the authenticated pure post-quantum v0.5 handshake with
authenticated bidirectional application traffic over BLE.

The v0.5 handshake remains unchanged:

- ML-KEM-768 key establishment;
- canonical transcript binding;
- transcript-bound v0.5 key schedule;
- six-digit SAS Numeric Comparison;
- explicit Central FINISHED verification;
- explicit Peripheral FINISHED verification;
- application traffic enabled only after successful authentication.

v0.6 adds:

- independent Central-to-Peripheral and Peripheral-to-Central traffic keys;
- encrypted application traffic in both BLE directions;
- independent sequence-number spaces;
- AES-256-GCM authentication and encryption in both directions;
- replay protection in both directions;
- rejection of application writes before authentication;
- hardware validation over three consecutive bidirectional round trips.

No classical ECDH or hybrid key establishment is introduced in v0.6.

---

## 2. Scope

Implemented in v0.6:

- directional application traffic-key derivation;
- generic embedded AES-256-GCM encrypt/decrypt primitives;
- Secure Data GATT WRITE + NOTIFY operation;
- authenticated Central-to-Peripheral application traffic;
- authenticated Peripheral-to-Central application traffic;
- independent send/receive sequence state;
- persistent authenticated session across multiple application messages;
- three hardware round trips:
  - `PING 0` → `PONG 0`
  - `PING 1` → `PONG 1`
  - `PING 2` → `PONG 2`
- negative tests for:
  - C→P AES-GCM tag tampering;
  - C→P replay;
  - P→C AES-GCM tag tampering;
  - P→C replay;
  - pre-authentication Secure Data writes.

Not introduced in v0.6:

- P-256 / ECDH;
- hybrid ML-KEM + ECDH key establishment;
- ML-DSA;
- modification of BLE SMP;
- persistent ML-KEM private keys;
- resumption;
- large application-message fragmentation;
- energy measurements;
- side-channel analysis;
- formal protocol verification.

---

## 3. Relationship with v0.5

The authenticated v0.5 handshake is preserved byte-for-byte at the
protocol level.

The v0.5 key schedule remains:

```text
key_block = HKDF-SHA256(
    IKM  = SS_MLKEM,
    salt = transcript_hash,
    info = "PQ-BLE-HANDSHAKE-v0.5/key-schedule",
    L    = 128
)

K_app        = key_block[0:32]
K_sas        = key_block[32:64]
K_finished_c = key_block[64:96]
K_finished_p = key_block[96:128]
