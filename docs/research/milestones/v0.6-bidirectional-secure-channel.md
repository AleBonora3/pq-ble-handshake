# v0.6 — Authenticated Bidirectional Secure Channel

**Status:** COMPLETE  
**Date:** 2026-09-05  
**Target:** nRF54L15 DK (`nrf54l15dk/nrf54l15/cpuapp`)  
**NCS:** 3.0.0  
**Zephyr:** 4.0.99  
**Central:** Windows + Python + Bleak + liboqs-python  
**Peripheral:** nRF54L15 DK + Zephyr/NCS + mlkem-native  
**BLE role:** PC Central ↔ nRF54L15 Peripheral  

---

## 1. Objective

v0.6 extends the authenticated pure post-quantum v0.5 handshake with
authenticated bidirectional application traffic over BLE.

The v0.5 handshake remains unchanged:

- ML-KEM-768 key establishment;
- production-random on-device ML-KEM KeyGen;
- canonical transcript binding;
- transcript-bound key schedule;
- six-digit SAS Numeric Comparison;
- explicit Central FINISHED verification;
- explicit Peripheral FINISHED verification;
- application traffic enabled only after successful authentication.

v0.6 adds:

- independent Central-to-Peripheral and Peripheral-to-Central traffic keys;
- encrypted application traffic in both BLE directions;
- independent sequence-number spaces;
- AES-256-GCM authentication and encryption in both directions;
- replay protection in both directions;
- rejection of application writes before authentication;
- multiple application messages within one authenticated connection epoch;
- hardware validation over three consecutive bidirectional round trips.

No classical ECDH or hybrid key establishment is introduced in v0.6.

---

## 2. Scope

Implemented in v0.6:

- directional application traffic-key derivation;
- generic embedded AES-256-GCM encrypt/decrypt primitives;
- Secure Data GATT WRITE + NOTIFY operation;
- authenticated Central-to-Peripheral application traffic;
- authenticated Peripheral-to-Central application traffic;
- independent send/receive sequence state;
- persistent authenticated state across multiple application messages;
- three hardware round trips:
  - `PING 0` → `PONG 0`;
  - `PING 1` → `PONG 1`;
  - `PING 2` → `PONG 2`;
- negative tests for:
  - C→P AES-GCM tag tampering;
  - C→P replay;
  - P→C AES-GCM tag tampering;
  - P→C replay;
  - pre-authentication Secure Data writes.

Not introduced in v0.6:

- P-256 / ECDH;
- hybrid ML-KEM + ECDH key establishment;
- ML-DSA;
- modification of BLE SMP;
- persistent ML-KEM private keys;
- persistent authenticated sessions;
- production hardware resumption;
- large application-message fragmentation;
- energy measurements;
- side-channel analysis;
- formal protocol verification.

## 3. Relationship with v0.5

The authenticated v0.5 handshake is preserved at the protocol level.

The canonical v0.5 transcript is:

```text
u16be(21)   || "PQ-BLE-HANDSHAKE-v0.5"
u16be(1)    || 0x01
u16be(1)    || 0x02
u16be(16)   || session_id
u16be(1184) || ML-KEM public key
u16be(1088) || ML-KEM ciphertext
```

Total canonical transcript size:

```text
2323 bytes
```

The transcript hash is:

```text
transcript_hash = SHA256(canonical_transcript)
```

The v0.5 key schedule remains:

```text
key_block = HKDF-SHA256(
    IKM  = SS_MLKEM,
    salt = transcript_hash,
    info = "PQ-BLE-HANDSHAKE-v0.5/key-schedule",
    L    = 128
)

K_app        = key_block[0:32]
K_sas        = key_block[32:64]
K_finished_c = key_block[64:96]
K_finished_p = key_block[96:128]
```

In v0.6, `K_app` becomes an authenticated application root key.

It is not used directly as an AES traffic key for v0.6 application traffic.

## 4. Directional Traffic-Key Derivation

The two v0.6 application traffic keys are derived as:

```text
K_c2p = HMAC-SHA256(
    K_app,
    "PQ-BLE-TRAFFIC-v0.6/CENTRAL-TO-PERIPHERAL"
)

K_p2c = HMAC-SHA256(
    K_app,
    "PQ-BLE-TRAFFIC-v0.6/PERIPHERAL-TO-CENTRAL"
)
```

where:

```text
K_c2p = Central -> Peripheral AES-256-GCM traffic key
K_p2c = Peripheral -> Central AES-256-GCM traffic key
```

The different HMAC labels provide explicit cryptographic direction separation.

`K_app` is already bound to the authenticated v0.5 transcript through the
v0.5 HKDF schedule, so v0.6 does not alter or duplicate the v0.5 handshake
KDF.

After Phase 6 traffic activation on the Peripheral, the retained `K_app`
application root is cleared and the two directional keys are retained for the
authenticated connection epoch.

## 6. Secure Application Wire Format

The existing authenticated application wire format is preserved:

```text
seq_num(8, big endian)
|| msg_type(1)
|| IV(12)
|| ciphertext(variable)
|| GCM tag(16)
```

Fixed overhead:

```text
8 + 1 + 12 + 16 = 37 bytes
```

AAD remains:

```text
session_id(16)
|| sender_role(1)
|| seq_num(8, big endian)
|| msg_type(1)
```

AAD size:

```text
16 + 1 + 8 + 1 = 26 bytes
```

Roles:

```text
Central    = 0x01
Peripheral = 0x02
```

Application DATA message type:

```text
0x01
```

Authenticated-encryption algorithm:

```text
AES-256-GCM
```

Each outgoing embedded application message receives a fresh 12-byte IV
generated through PSA Crypto.

## 7. Independent Sequence Spaces

v0.6 maintains two independent sequence-number spaces:

```text
Central -> Peripheral: 0, 1, 2, ...
Peripheral -> Central: 0, 1, 2, ...
```

Both directions can therefore legitimately begin at sequence number zero.

For received traffic, a frame is accepted only if:

```text
new_seq > last_accepted_seq
```

A received sequence number is committed to replay state only after successful
AES-GCM authentication.

Consequently, a forged frame containing an artificially high sequence number
cannot advance replay state before authentication succeeds.

Sequence and cryptographic session state are reset when the BLE
connection/session epoch is reset.

## 8. Generic Embedded Secure-Channel Primitives

v0.6 introduces generic embedded AES-GCM operations instead of limiting the
firmware to the former fixed P→C test message.

Encryption primitive:

```text
pq_secure_encrypt_with_key(...)
```

Decryption primitive:

```text
pq_secure_decrypt_with_key(...)
```

The generic decrypt operation:

1. validates frame structure;
2. parses sequence and message type;
3. performs preliminary replay checking;
4. reconstructs the expected AAD;
5. imports the AES-256 key through PSA Crypto;
6. authenticates/decrypts using AES-GCM;
7. exposes the accepted sequence only after authentication succeeds.

The existing Phase 3 / Phase 5 APIs remain available as compatibility wrappers.

## 9. BLE/GATT Integration

Secure Data was extended from notification-only operation to:

```text
WRITE   Central -> Peripheral
NOTIFY  Peripheral -> Central
```

The GATT layout remains unchanged:

```text
[0] Service
[1] Public Key declaration
[2] Public Key value
[3] Ciphertext declaration
[4] Ciphertext value
[5] Secure Data declaration
[6] Secure Data value
[7] CCCD
[8] Control declaration
[9] Control value
```

Total attributes:

```text
10
```

Secure Data therefore remains at:

```text
attrs[6]
```

No additional GATT characteristic was introduced.

Application cryptography is executed in the existing dedicated crypto worker
rather than directly inside the GATT WRITE callback.

## 10. Runtime State

After successful SAS and FINISHED processing, the connection reaches the
authenticated application state.

Unlike the original one-message application flow, v0.6 keeps the session
authenticated across multiple application exchanges.

Conceptually:

```text
v0.5 authenticated handshake
           |
           v
      AUTHENTICATED
           |
           +-- C->P Secure Data WRITE
           |          |
           |          v
           |    AES-GCM authenticate/decrypt
           |          |
           |          v
           |     application processing
           |          |
           |          v
           |      P->C AES-GCM encrypt
           |          |
           |          v
           +-- Secure Data NOTIFY
           |
           +-- remains AUTHENTICATED
```

Disconnect/session reset clears:

- `K_c2p`;
- `K_p2c`;
- Phase 6 session identifier;
- C→P replay state;
- P→C send-sequence state;
- retained authenticated application material.

## 13. Checkpoint 3 — Bidirectional Application Traffic

Checkpoint 3 replaced the temporary Phase 6 success ACK with genuine encrypted
Peripheral-to-Central application traffic.

For each valid `PING n`, the Peripheral:

1. authenticates/decrypts the C→P frame with `K_c2p`;
2. verifies the incoming sequence;
3. constructs `PONG n`;
4. encrypts the response with `K_p2c`;
5. uses its independent P→C send sequence;
6. sends the resulting secure wire through a BLE notification.

## 21. Security Properties Demonstrated

The v0.6 implementation provides experimental evidence for the following
properties in the tested configuration:

1. ML-KEM-derived authenticated application material can be separated into
   independent directional traffic keys.

2. Central and Peripheral use different AES-256-GCM keys for application
   traffic.

3. Central-to-Peripheral application data is authenticated and encrypted.

4. Peripheral-to-Central application data is authenticated and encrypted.

5. Both directions maintain independent sequence-number spaces.

6. Replayed application frames are rejected.

7. AES-GCM tag modifications are rejected.

8. Failed P→C authentication does not advance the Central receive sequence
   state.

9. Application writes are rejected before completion of the authenticated
   handshake.

10. Multiple application messages can be exchanged inside one authenticated
    BLE session.

11. The original authenticated v0.5 hardware path remains operational after
    v0.6 integration.

These results apply to the tested implementation and threat model and do not
constitute a claim of production readiness or formal protocol security.

## 25. Next Research Milestone

v0.6 intentionally remains a pure-PQ application-layer design.

The next milestone is a genuine application-layer hybrid handshake combining:

```text
ML-KEM-768
+
P-256 ECDH
```

The classical component will be generated and controlled by the application
protocol itself.

The design must not assume access to an internal BLE SMP ECDH shared secret.

The hybrid protocol will require:

- ephemeral P-256 key pairs;
- authenticated transport of both P-256 public keys;
- canonical transcript binding of both ML-KEM and ECDH material;
- a combiner requiring both shared secrets;
- hybrid SAS and FINISHED;
- v0.7 direction-separated application traffic;
- hybrid-specific negative testing;
- pure-PQ versus hybrid resource comparison.

Other later work includes:

- persistent authenticated-session storage;
- ML-DSA-based authentication;
- energy measurements;
- larger application payloads / fragmentation;
- side-channel analysis;
- formal protocol analysis.
