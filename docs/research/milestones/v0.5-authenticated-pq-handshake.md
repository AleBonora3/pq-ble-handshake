# v0.5 — Authenticated pure-PQ handshake

Status: COMPLETE — software, pristine-build, and physical nRF54L15 DK
validation completed. Positive authenticated E2E, production-random ML-KEM
KeyGen, SAS rejection, tampered FINISHED_C, tampered FINISHED_P, and
transcript/session mismatch tests all passed. Ready for v0.5 tagging.

This research milestone consolidates the pure ML-KEM-768 path. It does not add
P-256, a hybrid combiner, or bidirectional application traffic.

## Architecture

At boot, PSA Crypto initializes before the existing 28,672-byte crypto worker.
The worker obtains 64 bytes from `psa_generate_random()` and supplies them as
the `d || z` input to mlkem-native's deterministic ML-KEM-768 KeyGen API. The
coins are wiped immediately. The decapsulation key remains in DK-only RAM and
no coins, private key, shared secret, derived key, or FINISHED key is logged.
The separate opt-in deterministic ML-KEM self-test remains TEST-ONLY.

Phase 5 reuses the v0.4 GATT service and ciphertext fragmentation. ML-KEM,
transcript hashing, the key schedule, SAS/FINISHED HMAC operations, and the
final AES-GCM operation run on the crypto worker rather than a GATT callback.
An epoch cancels retained Phase 5 material and stale worker results on
disconnect. Connection references and generations prevent notification to a
replacement peer.

## Canonical transcript

The protocol domain is the 21 ASCII bytes:

```text
PQ-BLE-HANDSHAKE-v0.5
```

The canonical transcript is exactly 2,323 bytes. It contains six ordered
fields; every field is prefixed with its unsigned 16-bit big-endian byte
length:

```text
u16be(21)   || "PQ-BLE-HANDSHAKE-v0.5"
u16be(1)    || 0x01                         # Central role
u16be(1)    || 0x02                         # Peripheral role
u16be(16)   || session_id
u16be(1184) || ML-KEM-768 public_key
u16be(1088) || ML-KEM-768 ciphertext
```

Inputs with any other fixed field length are rejected. Neither endpoint sends
the transcript hash as a source of truth. Both compute:

```text
transcript_hash = SHA-256(canonical_transcript)
```

The Central serializes the transcript directly. The DK hashes the identical
serialization incrementally to avoid a 2,323-byte temporary buffer.

## Key schedule, SAS, and FINISHED

The key schedule is one 128-byte HKDF-SHA256 expansion:

```text
key_block = HKDF-SHA256(
    IKM  = SS_MLKEM,
    salt = transcript_hash,
    info = b"PQ-BLE-HANDSHAKE-v0.5/key-schedule",
    L    = 128
)

K_app        = key_block[0:32]
K_sas        = key_block[32:64]
K_finished_c = key_block[64:96]
K_finished_p = key_block[96:128]
```

The raw ML-KEM shared secret is wiped on the DK as soon as this block has been
split. Temporary key blocks are wiped. `K_sas` is used only for SAS; the two
FINISHED keys are direction-specific and are never used for AES.

SAS is computed independently on both endpoints:

```text
sas_mac = HMAC-SHA256(
    K_sas,
    b"PQ-BLE-HANDSHAKE-v0.5/SAS" || transcript_hash
)
sas = int.from_bytes(sas_mac, "big") mod 1_000_000
display = six decimal digits with leading zeroes
```

The full 256-bit HMAC is interpreted as one unsigned big-endian integer. The
DK computes the same reduction byte by byte. The SAS is displayed by the PC
and on the DK serial console; it is never transmitted as its source of truth.
The default user answer is no.

After explicit human confirmation:

```text
FINISHED_C = HMAC-SHA256(
    K_finished_c,
    b"PQ-BLE-HANDSHAKE-v0.5/FINISHED/C" || transcript_hash
)

FINISHED_P = HMAC-SHA256(
    K_finished_p,
    b"PQ-BLE-HANDSHAKE-v0.5/FINISHED/P" || transcript_hash
)
```

Both values are the full 32-byte HMAC output. The DK verifies `FINISHED_C`
with an explicit constant-time comparison. The PC verifies `FINISHED_P` with
`hmac.compare_digest`. Rejection or failure prevents the data request and AES
activation. SAS comparison is human authentication; FINISHED provides the
explicit bidirectional cryptographic key confirmation.

## GATT and wire protocol

The five existing characteristics and their attribute order are unchanged.
The existing ciphertext fragment is unchanged:

```text
idx(1) || total(1) || payload_len_be16(2) || payload
```

Phase 2 still uses `START` and `PQM2`. Phase 3 still uses
`START3 || session_id` and its v0.4 AES derivation.

Phase 5 starts with this Control write:

```text
"START5" (6 ASCII bytes) || session_id (16 bytes)       # total 22
```

All later Phase 5 handshake frames use:

```text
"PQS5" (4) || version=0x05 (1) || subtype (1)
|| payload_len_be16 (2) || payload
```

| Direction | Subtype | Value | Payload | Total |
|---|---|---:|---:|---:|
| Peripheral → Central notify | `READY_FOR_SAS` | `0x01` | empty | 8 B |
| Peripheral → Central notify | `FINISHED_P` | `0x02` | 32 B | 40 B |
| Peripheral → Central notify | `ERROR` | `0x7f` | status byte | 9 B |
| Central → Peripheral control | `FINISHED_C` | `0x10` | 32 B | 40 B |
| Central → Peripheral control | `DATA_REQUEST` | `0x11` | empty | 8 B |

Magic, version, declared length, subtype, payload length, connection, and
state are validated. Duplicate and out-of-order controls are rejected.

The Peripheral state progression is:

```text
IDLE -> CRYPTO_BUSY -> WAIT_FINISHED_C -> FINISHED_BUSY
     -> AUTHENTICATED -> DATA_BUSY -> IDLE
```

The Central has a separate explicit `WAIT_SAS_CONFIRM` state. On rejection it
enters `ABORTED` and sends neither FINISHED nor DATA_REQUEST.

The final request exists so notification timing cannot place application data
before Central verification of `FINISHED_P`. Its response reuses the existing
v0.4 application wire and AAD without weakening them:

```text
wire = seq_be64(8) || msg_type(1) || IV(12) || ciphertext || tag(16)
AAD  = session_id(16) || sender_role(1) || seq_be64(8) || msg_type(1)
```

For the first Peripheral-to-Central test payload, sequence is zero, sender role
is `0x02`, message type is `0x01`, plaintext is
`PQ-BLE SECURE CHANNEL`, and the wire length is 58 bytes. `K_app` is the AES-256
key. The current milestone does not add Central-to-Peripheral application data.

## Validated hardware evidence

The normal command completed twice on the physical nRF54L15 DK, including
after a power cycle:

```powershell
python -m src.central.main --phase5-auth-pq
```

Both runs completed ML-KEM encapsulation/decapsulation, independently produced
the same SAS, verified both direction-specific FINISHED values, and decrypted
`PQ-BLE SECURE CHANNEL`. Observed matching SAS values included `525723` and
`939837`.

Production-random KeyGen was separately checked across two power cycles. The
first 16 hexadecimal digits of the public-key SHA-256 fingerprint changed:

```text
boot 1: 168802e5a8a4edcd
boot 2: 27becddf8df08ef0
```

The user-rejection path was also validated by answering `n`. The Central
reported `SAS rejected; FINISHED and application data were not sent`; the DK
stopped after `Phase 5 READY_FOR_SAS notification sent`. No FINISHED value,
authenticated state, DATA_REQUEST, or AES application data followed.

The maximum cumulative crypto-worker stack result was:

```text
configured: 28672 B
peak:       23040 B
unused:      5632 B
```

This is 384 B above the v0.4 peak of 22,656 B and retains 5,632 B margin.

## Negative hardware test commands

All three modes use the unchanged production firmware image:

```powershell
python -m src.central.main --phase5-auth-pq --phase5-negative finished-c
python -m src.central.main --phase5-auth-pq --phase5-negative finished-p
python -m src.central.main --phase5-auth-pq --phase5-negative transcript
```

For `finished-c`, confirm the matching legitimate SAS. The Central then flips
only the final bit of the already-computed FINISHED_C. Success is an error
frame with authentication status `0x06`, or no FINISHED_P before timeout:

```text
NEGATIVE TEST PASS: tampered FINISHED_C rejected by Peripheral
PQ-BLE PHASE5 NEGATIVE TEST: PASS
```

For `finished-p`, confirm the matching legitimate SAS. The DK verifies the
legitimate FINISHED_C and sends its legitimate FINISHED_P; the Central flips
only the final bit of a local copy before `hmac.compare_digest`. It must not
send DATA_REQUEST:

```text
NEGATIVE TEST PASS: tampered FINISHED_P rejected by Central
PQ-BLE PHASE5 NEGATIVE TEST: PASS
```

For `transcript`, the real `START5 || session_id` is sent unchanged while the
Central flips bit zero of its local transcript session ID. Compare the
different SAS values and answer `n`:

```text
NEGATIVE TEST PASS: transcript mismatch detected by SAS
PQ-BLE PHASE5 NEGATIVE TEST: PASS
```

Entering `y` deliberately forces continuation with transcript-derived
FINISHED_C material that the DK must reject with status `0x06`. None of these
negative modes sends DATA_REQUEST after Central-side authentication failure.
Expected rejection exits with status zero; acceptance, an unexpected frame,
or another ambiguous failure exits nonzero.

## Remaining limitations

- The first validated application direction remains Peripheral → Central.
- There is no hybrid P-256 + ML-KEM construction yet.
- There is no energy benchmark or formal verification yet.
- liboqs 0.15.0 and liboqs-python 0.16.0 currently report a version warning.
- The research prototype uses the serial console as the Peripheral SAS display.
- This is a research prototype and is not described as production-ready.
